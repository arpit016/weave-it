# Session Capture: Architecture - 2026-06-08

## Summary

Discussed a workspace clone workflow for `weave add`: one user creates a workspace such as `pb-tm`, adds multiple repos, commits `.weave/workspace.yml` and `.gitignore`, and pushes the workspace. A teammate then clones the workspace. Because the repo folders are gitignored, the committed registry lists repos that are missing on disk.

The current `weave add` behavior treats a matching `workspace.yml` repo path as a duplicate before checking local availability. That makes the teammate workflow fail or report the wrong result: `weave add <git-url>` can say the repo is already registered even though it still needs to be cloned locally. For `weave add <local-path>`, the command can also report `already_exists` after adopting a missing registered repo, even though the local workspace was just materialized.

## Decisions Made

- Duplicate detection in workspace mode should mean "registered and present locally", not merely "registered in committed metadata".
- Missing registered repos should be materialized without rewriting committed workspace metadata.
- Matching should be path-based for now.
- For `weave add <git-url>`, use the URL-derived repo basename as the path match. If that path is registered but missing locally, clone into that registered path.
- For `weave add <local-path>`, use the destination basename/path as the path match. If that path is registered but missing locally, move the local folder into the registered workspace path.
- If the registered path is already present locally, keep returning `already_exists`.
- If the path is not registered, keep the existing register-and-gitignore behavior.

## Options Considered

- Match Git URLs by URL-derived path only. Accepted for this fix because it matches the current command model and keeps behavior predictable.
- Fall back to matching `remote` values in `workspace.yml`. Considered useful for renamed repos, but deferred to avoid broadening behavior beyond the immediate bug.
- Limit the fix to `weave add <git-url>`. Rejected because the same teammate-clone problem exists for local repo/folder adoption.

## Rejected Approaches

- Treating committed `workspace.yml` presence as sufficient evidence that a repo exists locally.
- Updating `.weave/workspace.yml` or `.gitignore` when materializing a repo that is already registered.
- Asking users to manually remove registry entries or edit metadata before they can clone/adopt missing repos.

## User Preferences

- Preserve the existing "move local repos/folders into the workspace" behavior, including `.git/` history.
- Keep the fix applicable to both `weave add <git-url>` and `weave add <local-path>`.
- Use simple path-based matching rather than remote-based matching for this iteration.

## Agent Recommendations

- Update `src/lib/add-folder.ts` so workspace duplicate handling checks local path availability before returning `already_exists`.
- Add a helper or small local branch structure that distinguishes three states: unregistered, registered-present, and registered-missing.
- For registered-missing paths, clone or move the repo/folder, then return a success message indicating the local workspace was materialized.
- Add regression tests in `tests/init.test.ts` for both URL clone and local path adoption against a pre-populated `workspace.yml`.
- Preserve the existing duplicate test for registered-present repos.

## Unresolved Points

- Exact user-facing wording and status for a materialized registered repo can be finalized during implementation. It should not look like an error or no-op.
- Remote-based matching for renamed repos remains a possible future enhancement.
