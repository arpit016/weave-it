# Session Capture: Exploration - 2026-06-02

## Summary

Closed the remaining knowledge-base exploration questions around authoring templates and validation scope.

The agreed direction is that knowledge templates should be guided but not strict schemas. They should give agents enough structure to write useful current-state behavioral specs, while allowing irrelevant sections to be omitted so small domains do not become ceremony-heavy.

The agreed v1 validation scope is scaffold, documentation, and skill contract guidance only. Weave should not add a CLI knowledge-structure validator in v1. Validation can be revisited after real repositories reveal which warnings would be useful.

## Decisions Made

- Use guided optional-section templates for `behavior.md`, `decision-tables.md`, `source-map.md`, and `knowledge-delta.md`.
- Treat `behavior.md` as the primary current-state behavioral spec.
- Strongly recommend `Purpose`, `Current Behavior`, `Source Anchors`, and `Change History` for behavioral specs.
- Allow agents to omit irrelevant template sections when the domain or feature does not need them.
- Use `decision-tables.md` only when behavior has important permutations or interaction rules.
- Use `source-map.md` to connect current behavior to source anchors, tests, configs, jobs, integrations, and ownership notes.
- Use `knowledge-delta.md` as the per-change bridge from historical work to current-state knowledge.
- Do not add CLI validation for knowledge structure in v1.
- Rely on scaffold/docs plus `weave-knowledge` skill guidance and skill contract tests in v1.
- Treat future CLI validation as a later enhancement after real usage shows which warnings are valuable.

## Options Considered

- Strict required sections for every knowledge file.
- Minimal templates with only a few headings.
- Guided optional sections with strongly recommended anchors.
- Full CLI validation for knowledge folder structure in v1.
- Lightweight CLI warnings in v1.
- No CLI validation in v1, with scaffold/docs and skill contract guidance.

## Rejected Approaches

- Strict required templates, because small domains and simple features should not be forced into heavy documents.
- Minimal templates, because they would not reliably produce behavioral specs that future agents can reason from.
- Full CLI validation in v1, because it would create a new product surface and likely false positives before the workflow has been used in real repos.
- Lightweight CLI warnings in v1, because warning policy still needs real-world evidence.

## User Preferences

- Prefer guided optional templates.
- Prefer no CLI validation in v1.
- Keep v1 focused on scaffold, docs, and skill behavior.
