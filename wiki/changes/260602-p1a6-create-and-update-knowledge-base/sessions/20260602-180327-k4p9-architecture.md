# Session Capture: Architecture - 2026-06-02

## Summary

Created the implementation architecture for the knowledge base workflow. The design covers scaffold changes, change lifecycle metadata, the new `weave change knowledge <status>` command, the new `weave-knowledge` skill, `weave-next` advisory behavior, docs, and tests.

## Decisions Made

- V1 will scaffold the standard knowledge folders and README guidance, but will not add full CLI validation for the knowledge folder structure.
- Knowledge freshness will live in `status.yml.knowledge` with `pending`, `stale`, `updated`, and `none` statuses.
- `weave change knowledge <status>` will be the CLI-owned write path for knowledge lifecycle state.
- The command will support `--target`, repeatable `--domain`, repeatable `--shared`, repeatable `--file`, `--delta`, `--reason`, `--invalidated-by`, and `--json`.
- `weave change progress <lane>` will mark previously resolved knowledge as stale when lifecycle artifacts change after knowledge was marked `updated` or `none`.
- `weave-next` will remain read-only and report knowledge freshness instead of mutating it.
- `.weave/sync.yml` will continue to track only `wiki/knowledge/index.md` in v1.

## Options Considered

- Full CLI validation for knowledge structure in v1.
- Scaffold/docs plus skill contract guidance in v1.
- Treating knowledge as a normal lifecycle lane.
- Tracking knowledge freshness in `tasks.md`.
- Tracking knowledge freshness in `status.yml`.

## Rejected Approaches

- Full v1 validation was rejected because it would introduce a new policy-heavy product surface before real repositories reveal useful warnings.
- Treating knowledge as a normal artifact lane was rejected because knowledge is current-state product memory, not a sequential change artifact.
- Using `tasks.md` for knowledge freshness was rejected because lifecycle state is already owned by `status.yml` and CLI commands.

## User Preferences

- Keep the knowledge base useful for large codebases and heavy domains.
- Use behavioral specs as a common model that can extend across domains.
- Keep templates structured enough to guide agents but not so rigid that every page becomes ceremony.
- Preserve user control over existing knowledge organization; agents may create missing standard files but should not reorganize user-authored knowledge without approval.

## Agent Recommendations

- Add typed parsing for `status.yml.knowledge` while preserving unknown status fields for backward compatibility.
- Keep scaffold writes non-overwriting.
- Update bundled skill templates and installed repo copies together, with tests that assert alignment.
- Add status output and JSON coverage so agents can reliably inspect knowledge freshness.
