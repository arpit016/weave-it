# Session Capture: Exploration - 2026-06-02

## Summary

Discussed how Weave should support a durable knowledge base that remains useful when teams return to a product area months after multiple changes, bug fixes, removals, and feature additions.

The agreed framing is that `wiki/changes/**` is historical provenance, while `wiki/knowledge/**` should be current-state product and system truth. For complex product domains, knowledge should behave like a living behavioral spec, not a loose documentation dump or chronological change log.

Performance reviews were used as the motivating domain. The domain has many dimensions and combinations, such as self review with or without goals, peer review, upward review, downward or manager review, calibration, visibility, and permissions. The knowledge base should help future agents reason about the complete behavioral model, but should avoid enumerating every permutation as repetitive prose.

## Decisions Made

- Treat knowledge pages as current-state behavioral specs.
- Keep change artifacts as history and provenance, not the primary place to understand current behavior.
- Use dimensions, rules, decision tables, lifecycle, permissions, edge cases, invariants, and source anchors to represent complex domain behavior.
- Avoid a single giant domain file for heavy domains.
- Use a hierarchical knowledge structure for large domains:
  - domain-level overview and navigation
  - feature-level behavioral specs
  - cross-feature specs for interactions inside a domain
  - cross-cutting specs for concerns shared across multiple domains
- Future work should discuss knowledge folder structure before enforcement, skills, staleness, or init behavior.

## Options Considered

- Flat domain page with one `behavior.md` per domain.
- Domain folder with `index.md`, `overview.md`, `glossary.md`, and `source-map.md`.
- Feature-level specs under `features/<feature>/behavior.md`.
- Domain-local cross-feature specs under `cross-feature/`.
- Repo-wide cross-cutting specs under `wiki/knowledge/cross-cutting/`.
- Per-change `knowledge-delta.md` as a bridge from implementation history into current knowledge.
- Knowledge closure tracked from active change state or `tasks.md`.

## Rejected Approaches

- Relying only on historical change artifacts to answer how the product behaves today.
- Treating the knowledge base as a chronological log of changes.
- Creating a page for every UI screen or API endpoint instead of product behavior users and engineers reason about.
- Forcing every complex domain into a single `behavior.md` file.
- Listing every product permutation as unstructured prose when dimensions and decision tables can describe behavior more scalably.

## User Preferences

- The knowledge base should be detailed enough to behave like a behavioral spec.
- The approach must scale to large codebases and complex product domains.
- The folder structure needs explicit treatment, including the purpose of each file.
- The next discussion should start with the folder structure question before moving into enforcement or workflow design.
- The user explicitly wants to pause the session and resume later from the open questions.

## Agent Recommendations

- Use `wiki/knowledge` as a current-state behavioral spec layer.
- Organize heavy domains hierarchically:
  - `index.md` as navigation
  - `overview.md` as domain summary
  - `glossary.md` when domain language is substantial
  - `source-map.md` for code, tests, APIs, schemas, and ownership anchors
  - `features/<feature>/behavior.md` for independently understandable behavior areas
  - `cross-feature/<topic>.md` for interactions inside the same domain
  - `cross-cutting/<topic>/behavior.md` for concerns that apply across multiple domains
- Split a feature into its own spec when it has its own lifecycle, permissions, configuration, edge cases, frequent independent changes, dedicated source anchors, or when a single page becomes too large to scan.
- Keep future knowledge pages focused on current truth with source anchors and links to relevant change IDs.
