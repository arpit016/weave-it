# Session Capture: Exploration - 2026-06-02

## Summary

Resumed exploration for the knowledge base change and converted the prior brainstorming into a decision-complete product direction.

The knowledge base should be a current-state behavioral spec layer for product and system domains. Change folders remain historical provenance, while `wiki/knowledge/**` should answer how the product behaves today. The structure should scale from small repositories to large domains with many features and cross-domain behaviors.

The discussion refined the folder names to use plain language:

- `domains/` for product or system domains
- `features/` for feature-level behavior inside a domain
- `domain-wide/` for behavior coordinating multiple features inside one domain
- `shared/` for behavior reused across multiple domains

## Decisions Made

- Standardize the top-level knowledge structure around `domains/` and `shared/`.
- Replace the earlier `cross-feature/` term with `domain-wide/`.
- Replace the earlier `cross-cutting/` term with `shared/`.
- Treat centralized approval workflow as `shared/approvals` when multiple domains use the same approval behavior.
- Use `domain-wide/approvals.md` inside a domain to describe domain-specific approval integration or overrides.
- Use a guide-and-validate enforcement model: Weave should scaffold and warn, but not block nonstandard existing structures.
- `weave init` should create standard knowledge folders plus a top-level README explaining the folder structure and showing a sample tree.
- Agents may create missing standard folders/files for active knowledge updates, but must not reorganize or move existing user-authored knowledge without explicit approval.
- Add a `weave-knowledge` skill that creates or updates both `knowledge-delta.md` and current-state `wiki/knowledge/**` specs.
- Track knowledge freshness in `status.yml`, not in `tasks.md`.
- Use knowledge lifecycle statuses `pending`, `stale`, `updated`, and `none`.
- Add a CLI-owned lifecycle command shaped as `weave change knowledge <status>`, rather than asking skills to hand-edit `status.yml`.

## Options Considered

- Formal `domains/` and `cross-cutting/` folders.
- Loose domain folders directly under `wiki/knowledge`.
- Hybrid aliases for formal and legacy paths.
- `shared/`, `shared-behavior/`, `platform/`, `common/`, `global/`, and `foundation/` as alternatives to `cross-cutting/`.
- `cross-feature/`, `domain-wide/`, and direct feature-owned files for within-domain interactions.
- `weave change knowledge <status>`, `weave change progress knowledge`, and `weave knowledge status` as command shapes.
- `status.yml`, `tasks.md`, and dual tracking for knowledge freshness.

## Rejected Approaches

- Use `cross-cutting/` and `cross-feature/` as final folder names, because they are less self-explanatory for users and agents.
- Treat knowledge as just another `weave change progress` lane, because knowledge has freshness and no-impact states rather than ordinary artifact progress.
- Let skills hand-edit `status.yml`, because existing lifecycle state is CLI-owned.
- Use `tasks.md` as the authoritative knowledge lifecycle source.
- Allow agents to silently reorganize existing knowledge folders.
- Create noisy fake example domains during `weave init`.

## User Preferences

- Prefer self-explanatory folder names over technically precise but opaque terms.
- Use `shared/` for behavior reused across multiple domains.
- Use `domain-wide/` for behavior spanning multiple features inside one domain.
- `weave init` should create standard folders and a README explaining the structure with a sample folder tree.
- Agents can create missing standard folders/files, but should not reorganize existing structure without approval.
- Knowledge updates should be manually triggered by users through `weave-knowledge`.
- `status.yml` should always show whether knowledge is updated, pending, stale, or none.
- If anything upstream in the pipeline becomes stale, knowledge should become stale too.

## Agent Recommendations

- Keep `wiki/knowledge/index.md` as a live catalog of actual knowledge areas.
- Add `wiki/knowledge/README.md` as the durable structure guide and authoring rule reference.
- Use README files under `domains/` and `shared/` so the scaffold is Git-trackable without fake examples.
- Make `weave-knowledge` orient and ask when there is no active change or ambiguous target knowledge area.
- Let `weave-next` surface knowledge status and recommend `weave-knowledge` when knowledge is pending or stale.
- Missing knowledge metadata in older changes can imply unknown rather than adding an explicit `unknown` status.

## Unresolved Points

- Exact `status.yml.knowledge` field shape.
- Exact option names for `weave change knowledge <status>`.
- Whether `weave-next` should mark knowledge stale automatically when stale artifact lanes exist, or only report the relationship.
- The detailed authoring templates for `behavior.md`, `decision-tables.md`, `source-map.md`, and `knowledge-delta.md`.
- Whether this change should add full CLI validation or only scaffold/docs plus skill contract guidance in v1.
