# Session Capture: Exploration - 2026-06-10

## Summary

Exploration focused on whether Weave should remove hidden local session state used as workflow routing: `current_change` and `current_artifact` in the user-local current session file. The discussion clarified that the concern is not the npm-version cache, but the local `current-session.yml` style state that lets commands and skills operate from saved context even when the current branch or current conversation lane does not clearly identify the intended change or artifact.

The emerging product direction is to make active change resolution branch-derived and make discussion/capture lane resolution explicit or conversation-derived, rather than persisting hidden local pointers.

## Decisions Made

- Treat the git branch as the primary active-change source of truth: a branch named `change/<change-id>` should silently identify the active change when the matching `wiki/changes/<change-id>/status.yml` exists.
- When the current branch does not follow `change/<change-id>`, agents should stop and ask the user to create or switch to a change instead of relying on a saved local active-change pointer.
- Staleness remains durable in `status.yml`; removing local active-change state only changes how Weave chooses which change's `status.yml` to read or mutate.
- Remove `current_artifact` as hidden persisted lane state. The current discussion lane is invocation/conversation context, not durable product state.
- Bare `weave-capture` should be allowed to infer a lane from visible recent skill invocation and conversation substance when that signal is strong, but should ask the user when the lane is missing, mixed, or contradictory.
- `weave-clarify architecture` is the right skill for restructuring an already-captured architecture into facets. `weave-architect` remains the thinking/interview skill; `weave-capture architecture` persists a fresh architecture discussion.

## Options Considered

- Keep `current_change` and `current_artifact` in the local session and improve validation. Rejected directionally because it preserves the hidden stale-pointer class of bugs.
- Keep only a fallback local active-change pointer for non-git folders. Rejected directionally unless a strong non-git workflow emerges, because it would keep an inconsistent exception to the branch-derived model.
- Make bare `weave-capture` always ask for a lane. Considered safest, but may be too noisy when the immediately preceding skill and conversation clearly identify the lane.
- Infer `weave-capture` lane from the last invoked skill and conversation substance without persisting it. Preferred over local state, with an explicit ask on ambiguity.

## Rejected Approaches

- Treating this as the npm latest-version cache problem. The npm cache is separate and not the source of the observed workflow bug.
- Continuing to require Plan Mode skills such as `weave-explore` and `weave-architect` to write `current_artifact` before discussion. This is the specific failure mode the user is seeing: Plan Mode often fails to update the stored lane.
- Letting sub-repo branches decide workspace artifact staleness. In workspace mode, staleness belongs to the workspace root change artifact, not individual implementation repo branches.

## User Preferences

- Strong preference to remove hidden local active-change and current-artifact state because it is the main source of observed confusion.
- Preference that branch shape (`change/<change-id>`) silently identifies the active change; only non-matching branch shapes should require user intervention.
- Preference for agents to ask the user to create or switch to a change when no branch-derived active change is available.
- Interest in keeping `weave-capture` convenient by inferring the lane from the skill invoked in the session when that signal is obvious.

## Agent Recommendations

- Split the change into two slices: remove `current_artifact` first, then replace `current_change` with branch-derived active-change resolution.
- Keep durable staleness mechanics unchanged in `status.yml`.
- In workspace mode, make the workspace root branch the active-change authority; registered sub-repo branches are implementation state and should not select the change artifact.
- Update bundled and installed skill contracts together, because current skills explicitly call or read `weave artifact current`.
- Treat this as a product workflow simplification before architecture work: the key user behavior is replacing hidden state with observable branch and explicit/conversation lane selection.

## Unresolved Points

- In workspace mode, confirm whether the workspace root branch should be the only active-change authority even when the user is currently inside a registered sub-repo whose own branch is `change/<id>`.
- Decide whether non-git folders should lose implicit active-change support entirely or receive an explicit alternative.
- Decide exact bare `weave-capture` behavior: infer silently when last invoked skill and discussion substance agree, or always ask for a lane.
- Decide whether `weave artifact current` should be removed, deprecated with a compatibility warning, or repurposed to report no stored lane.
