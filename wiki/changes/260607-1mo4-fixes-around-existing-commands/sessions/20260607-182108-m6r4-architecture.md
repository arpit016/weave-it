# Session Capture: Architecture - 2026-06-07

## Summary

The follow-up architecture discussion identified the likely root cause of `weave-architect` skipping its lane commit. The problem is not just that the command needs verification; the opening contract says the skill "never creates, edits, renames, deletes, or progresses repo-tracked artifacts." That sentence is technically about repo-tracked artifacts, but it is early and strong enough that agents over-apply it to local session-state writes in Plan Mode.

The fix should first clarify the top-level read-only contract: `weave-architect` must not write repo-tracked artifacts, but it may update local Weave session state to record the `architecture` lane. Verification remains useful, but it should not block the architecture discussion if the lane cannot be set.

## Decisions Made

- Revise the top-level `weave-architect` read-only wording so it explicitly separates repo-tracked artifact writes from local Weave session-state writes.
- Keep `weave artifact current set architecture --json` as the architecture lane entry command.
- Keep successful lane commits silent.
- Add `weave artifact current --json` verification after the lane commit.
- If verification shows the lane is still not `architecture`, continue the architecture discussion and show a concise warning that `weave-capture` may ask for the target later.
- Do not stop `weave-architect` solely because the stored lane could not be updated.

## Options Considered

- Failing fast when the lane commit fails was rejected because the architecture discussion remains valuable and `weave-capture` already has defensive lane verification.
- Relying only on command inlining was rejected because the command is already inlined and the problem still occurred.
- Leaving the top-level "never creates, edits..." sentence unchanged was rejected because it creates the wrong Plan Mode instinct.

## Rejected Approaches

- Do not remove the read-only contract entirely.
- Do not allow `weave-architect` to write repo-tracked artifacts.
- Do not make lane verification a hard blocker.
- Do not print raw command output for successful lane commits.

## User Preferences

- `weave-architect` should continue even if it cannot update the stored lane.
- The user should see a warning only when the stored lane could not be updated.
- The skill text should prevent agents from misreading local session-state writes as forbidden artifact writes.

## Agent Recommendations

- Replace the current opening text:
  `It never creates, edits, renames, deletes, or progresses repo-tracked artifacts.`
- Use wording like:
  `This skill never creates, edits, renames, deletes, or progresses repo-tracked artifacts. It may update local Weave session state only to record that the active artifact lane is architecture via weave artifact current set architecture --json.`
- Keep the verification command and non-blocking warning in the resolve context section.
- Update template and installed copies together.
- Add test assertions for both the clarified top-level contract and non-blocking verification warning.

## Unresolved Points

- Exact final wording can be tightened during implementation, but it must preserve the distinction between repo-tracked artifacts and local session state.
