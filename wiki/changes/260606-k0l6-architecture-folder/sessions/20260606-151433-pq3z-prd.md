# Session Capture: PRD - 2026-06-06

## Summary

Brainstormed the product behavior for converting the architecture artifact from a single `architecture.md` file to a folder shape (`architecture/` with `index.md` + facet files), making `weave-architect` strictly read-only, introducing a user-customizable architect template kit, and extending `weave-capture` and `weave-clarify` to perform facet-aware writes and structural refactors. Workspace-mode multi-repo context gathering for `weave-architect`/`weave-capture`/`weave-clarify` was explicitly deferred to a follow-up change.

## Decisions Made

- Default architecture artifact shape is a folder (`architecture/index.md` + optional facet files); index-only is the minimal shape.
- Backward compat: legacy single-file `architecture.md` keeps working. Both shapes coexisting in one change is an error. Migration is opt-in via `weave-clarify`, never automatic.
- Default architect template kit ships `{index-template.md, schema-template.md, api-contract-template.md, frontend-backend-template.md}`. Users add more by dropping `<facet>-template.md` into the installed templates folder.
- Strict naming convention: only files matching `<facet>-template.md` count as templates.
- Each `*-template.md` carries frontmatter `facet: <id>` and `description: <one-line>` so capture/clarify can explain routing decisions.
- `weave-architect` becomes read-only forever. It reads existing change context (PRD, sessions, decisions, contracts, existing `architecture.md` or `architecture/` files), workspace-level knowledge, and codebase, then interviews and dissects. It never writes any file. It never reads the templates folder.
- `weave-architect` accepts a free-form topic argument (`weave-architect schema`, `weave-architect cache-strategy`, etc.). The topic scopes the interview only; it is not validated against any registered facet list.
- Architect's output is a structured dissection presented in chat; capture takes that conversation as input.
- `weave-capture` is the writer for the architecture lane. It owns template loading, facet routing, refactor primitives, and the cross-facet contradiction check.
- Capture's routing decision tree, in order: (1) topic matches an installed `<facet>-template.md` → write/merge into `architecture/<facet>.md`; (2) no template, content fits an existing facet's scope → merge there; (3) cross-cutting or small → add to `architecture/index.md`; (4) user explicitly asked for a separate facet → create `architecture/<name>.md` with no synthesized structure (just the discussion content); (5) default fallback → index.md cross-cutting section.
- When user explicitly forces a new facet without a matching template, capture creates the file using only the discussion content. No skeleton, no fabricated headings.
- `weave-clarify` learns the folder shape and gains structural refactor primitives shared with capture: create-facet, split, merge, rename, delete, move-content, update-index. Clarify is the verb for pure structural refactors (no new content).
- Capture is the verb when the discussion includes both new content and refactor decisions intertwined; capture handles both atomically.
- Both skills detect refactor intent in natural language (no formal section header convention). Both surface contradictions in `architecture/index.md` Open Questions but never block writes.
- All facet-targeting and refactor operations use skill invocation + natural-language directives. No new CLI flags.
- Cross-lane invocation works mechanically because both skills accept an explicit lane: a user "in" weave-issues can still invoke `weave-clarify architecture` or `weave-capture architecture` and they target architecture regardless of ambient lane state.
- Session notes stay lane-level. Frontmatter additively gains `facets: [<id>, ...]` listing facets the discussion durably touched. Legacy notes without `facets:` are treated as lane-level (covering all facets) for backward compat.
- Per-facet resume filtering uses the new frontmatter array plus each facet file's filesystem mtime as the per-facet `updated_at` proxy. No metadata block per facet.
- Lifecycle is lane-atomic. `weave change progress architecture --source ...` runs once per capture/clarify operation regardless of how many facet files changed. `status.yml.artifacts.architecture` does not need a shape change.
- Skill installer is generalized to handle a templates folder under `weave-architect/`, with the same user-edit preservation model from `260605-wohe-customizable-prd-template`. User-added template files survive updates trivially.
- All of the above ships as one Weave change rather than splitting across multiple, to avoid half-working intermediate states.
- Workspace-mode multi-repo context gathering (architect/capture/clarify walking each registered sub-repo's code, docs, and sub-wikis) is explicitly deferred to a separate follow-up change.

## Options Considered

- Folder shape: always-folder, hybrid (single-file unless user opts in), or always-folder with index-only minimal. Closed at always-folder + index-only minimal.
- Template discovery: convention-based (any `<facet>-template.md`) vs manifest-based (`manifest.yml` listing valid facets). Closed at convention-based.
- Facet propagation from architect to capture: extend `weave artifact current set` with `--facet` flag; rely on capture's own analysis; accept facet as required arg; or capture takes facet as optional override only. Closed at "capture analyzes independently"; no propagation handshake.
- Capture fallback when discussion topic has no matching template: ship a generic fallback template; ask the user; merge into closest existing facet; add to index only; or merge into existing docs by default with explicit user override creating an ad-hoc facet. Closed at the last option.
- Architect: also reads templates to scope the interview vs. never reads templates. Closed at never reads templates.
- Architect: writes Plan-Mode-only and otherwise writes the artifact, vs. never writes period. Closed at never writes period.
- Refactor signaling from architect dissection: formal section-header convention vs. natural language. Closed at natural language.
- Session notes: lane-level only; per-facet (one note per facet); lane-level with `facets:` array; or hybrid lane-vs-facet by context. Closed at lane-level with `facets:` array.
- Whether to extend `weave-clarify` in the same change. Closed at yes (otherwise users hit a half-working state).
- One mega-change vs. three smaller (shape, kit, context-gathering). Closed at one change for shape+kit+architect-rewrite+capture+clarify; multi-repo context gathering is the only deferred piece.

## Rejected Approaches

- Architect reads template kit to scope its interview. Rejected because templates are a writing concern, not a thinking concern; coupling architect to templates makes the skill rigid and doubles the surface area users must learn.
- Architect writes files in non-Plan Mode. Rejected because it created a bipolar skill (advisor in Plan Mode, writer outside) that contradicted the existing v1 intent in `weave-capture`'s "Missing Artifact Creation" section.
- Auto-create new facet files for any topic discussed. Rejected because templates should gate file creation; otherwise the folder explodes with thin files and the user loses control of structure.
- Synthesizing a generic skeleton when capture is forced to create a facet without a template. Rejected because the user said "no need to follow any template" — the discussion content alone is the file.
- Tracking `current_facet` in local Weave session state via a CLI extension to `weave artifact current set`. Rejected because capture is intelligent enough to detect facets from conversation content (mirrors the existing Defensive Lane Verification pattern).
- New CLI flags like `--facet`, `--new-facet`, `--migrate-to-folder`. Rejected because every operation is expressible as skill invocation + natural language; no new CLI surface needed.
- Splitting this change into multiple smaller PRDs. Rejected because architect rewrite, folder shape, template kit, and capture/clarify extensions are tightly coupled and would otherwise leak partial-state behavior.
- Auto-migrating legacy `architecture.md` to folder shape on next write. Rejected because surprising users with layout changes is worse than asking them to opt in via clarify.

## User Preferences

- Strong preference for skills doing the thinking and the CLI staying small. No new CLI flags; everything routed through natural-language skill invocation.
- Strong preference for clean role separation: architect = thinking partner, capture = writer, clarify = restructurer. No skill should do two jobs.
- Strong preference for user-extensibility without skill modification. Drop a `*-template.md` file → the system picks it up; no skill edit required.
- Preference for templates being a writing concern only. Architect explicitly should not load templates.
- Preference for capture deciding placement intelligently rather than coupling architect's invocation to capture's writes.
- Preference for cross-lane refactoring: from any lane, the user should be able to refactor architecture facets via either capture (when content is new) or clarify (when refactor is pure).
- Preference for one well-scoped change rather than multiple staged ones for this work.

## Agent Recommendations

- Implementation order: ship templates first (default kit + frontmatter), generalize installer, then architect rewrite, then capture extensions, then clarify extensions, then knowledge/README updates.
- Document the routing decision tree in capture's SKILL.md so the user can predict capture's placement choices.
- Document the structural refactor primitives identically in capture and clarify SKILL.md to prevent behavioral drift between the two writers.
- Surface the "both shapes present" error consistently across capture, clarify, and any consumer that reads the artifact.
- After this change ships, scope the workspace-mode multi-repo context-gathering follow-up (architect/capture/clarify walk each `repos[]` entry's code, internal docs, and sub-wiki) as the natural successor.
