# Session Capture: Architecture - 2026-06-06

## Summary

Captured the architecture direction for the folder-based architecture artifact and template kit change. The implementation should add a shared architecture artifact resolver, keep architect templates as direct child skill resources beside `SKILL.md`, rewrite `weave-architect` as read-only, update capture/clarify/reader skills for folder mode, and make `weave-issues` the downstream coverage and consistency gate before task writing.

## Decisions Made

- Add a reusable TypeScript architecture artifact resolver instead of leaving shape detection only in skill instructions.
- The resolver should handle legacy file mode, folder mode, shape conflicts, and missing/non-substantive architecture.
- Folder-mode architecture is substantive when `architecture/index.md` is substantive or any facet file under `architecture/*.md` is substantive.
- If only facets are substantive, readers should treat architecture as usable but partial.
- Keep architect templates as direct child resources beside `weave-architect/SKILL.md`: `index-template.md`, `schema-template.md`, `api-contract-template.md`, and `frontend-backend-template.md`.
- Do not add nested resource support for `weave-architect/templates/`; the existing installer already supports direct child `.md` resources.
- Update `src/lib/changes.ts` hardcoded architecture checks so lifecycle/source heuristics understand folder-mode architecture.
- Update skill templates that read/write architecture so they no longer hardcode only `architecture.md`.
- `weave-issues` should not require PRD or architecture to exist. It should verify PRD coverage and/or architecture coverage opportunistically when those artifacts exist and are usable.
- When both PRD and architecture exist, `weave-issues` should check PRD/architecture consistency before writing tasks.

## Options Considered

- Shared code helper vs skill-only shape text: selected shared code helper because CLI lifecycle heuristics already hardcode `architecture.md`.
- Nested template folder vs flat direct child resources: selected flat direct child resources because current installer already supports them and avoids nested resource semantics.
- Index-required vs index-or-facet substance: selected index-or-facet for a less rigid, incremental user workflow.

## Rejected Approaches

- Skill-instruction-only architecture resolution. Rejected because internal code in `src/lib/changes.ts` would still miss folder-mode architecture.
- Nested `weave-architect/templates/*.md` resources. Rejected because direct child resources are already supported and sufficient.
- Requiring `architecture/index.md` to be substantive before any architecture is usable. Rejected as too restrictive; facet-first architecture capture should still be useful.
- Requiring PRD or architecture before `weave-issues`. Rejected because `weave-issues` should use whatever source context exists.

## User Preferences

- Prefer flexible, non-rigid behavior.
- Prefer minimal CLI surface and natural-language skill invocation.
- Prefer direct skill resource templates over nested template folder semantics.
- Prefer downstream verification in `weave-issues` rather than blocking earlier architecture capture.

## Agent Recommendations

- Implement a shared resolver in `src/lib/architecture-artifact.ts` and use it from `src/lib/changes.ts`.
- Keep template resources direct children of `templates/skills/weave-architect/`.
- Update `weave-issues` to perform coverage/sync review before writing tasks, but only for source artifacts that exist.
- Update reader skills to load `architecture/index.md` first when substantive, and otherwise use substantive facet files with a partial-architecture warning.
- Add tests for the resolver, direct resource install/reset/update behavior, skill template expectations, and lifecycle source inference.
