# Session Capture: Exploration - 2026-06-01

## Summary

Explored whether Weave should keep strict artifact prerequisites and linear lifecycle stale tracking. The agreed direction is to make artifact creation independent and make lifecycle staleness depend on actual artifact sources rather than fixed lane order.

The user called out future change types such as bug fix, tech debt, and refactor, where `prd.md` is often unnecessary and `architecture.md` or technical planning is usually the useful artifact.

## Decisions Made

- Remove the universal constraint that `prd.md` requires usable `exploration.md`.
- Remove the universal constraint that `architecture.md` requires `prd.md`.
- Treat exploration, PRD, architecture, and issues as available artifact lanes, not a mandatory pipeline for every change.
- Make change type influence expected artifacts and next-step recommendations.
- For PRD creation without enough upstream context, `weave-prd` should interview until product decisions are sufficiently resolved.
- For architecture creation without enough PRD context, `weave-architect` should use architecture sessions, current discussion, codebase inspection, and interview until technical decisions are sufficiently resolved.
- Keep `source` for backward-compatible display and add structured `sources` metadata for dependency checks.
- Make stale tracking source-aware instead of lane-order-aware.

## Options Considered

- Keep the strict `exploration -> prd -> architecture -> issues` pipeline for all changes.
- Remove stale tracking entirely.
- Keep stale tracking but make it source-aware.
- Represent artifact provenance only with the existing `source` string.
- Add a `sources` list while preserving `source`.
- Use a more structured source object.

## Rejected Approaches

- Reject a universal product pipeline for every change type, because fixes, refactors, tech debt, docs, tests, CI, and chores often do not need a PRD.
- Reject lane-order staleness as the sole rule, because direct architecture creation should not imply PRD exists or that PRD changes automatically invalidate architecture.
- Reject a complex source object for now; it is precise but heavier for skills and users.

## User Preferences

- The user wants change type to influence which artifacts are expected.
- The user sees the full pipeline as valid mainly for feature-style work.
- The user wants bug fixes, refactors, and tech debt to be able to proceed primarily through architecture or technical planning.
- The user prefers source-aware stale tracking over removing stale tracking entirely.
- The user chose a `sources` list as the metadata shape for source-aware lifecycle behavior.
- The user wants this captured as a new Weave change, not folded into the older pending-session change.

## Agent Recommendations

- Update `weave-prd`, `weave-architect`, and `weave-capture` to remove hard upstream prerequisite gates.
- Update `weave-next` to make type-aware recommendations instead of assuming one forward pipeline.
- Add artifact frontmatter parsing for `source` and `sources`.
- Update lifecycle logic so stale markers are based on artifact source dependencies.
- Keep `stage` as rough orientation for now, but stop using it to infer skipped upstream artifacts.
- Treat adding `tech-debt` as a likely follow-up unless explicitly included in this change.

## Unresolved Points

- Whether this change should include adding `tech-debt` as a first-class change type.
- Exact source vocabulary beyond file sources, such as `discussion`, `sessions`, and `codebase`.
- Whether source-aware stale should support transitive dependency invalidation in v1 or only direct dependencies plus issue/task evidence.
- Whether `weave change progress` should keep its current name after becoming source-aware.

Created and populated `exploration.md` for the new source-aware artifact lifecycle change.
