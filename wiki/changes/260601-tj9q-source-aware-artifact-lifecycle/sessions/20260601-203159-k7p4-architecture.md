# Session Capture: Architecture - 2026-06-01

## Summary

The architecture discussion refined the source-aware lifecycle design after the PRD was generated. The key shift is that dependency metadata should not live as new machine-readable `sources` frontmatter in each artifact. Instead, the CLI should own a dependency graph in `status.yml`, while artifact frontmatter keeps the existing `source` field as display/backward-compatible context.

The architecture plan keeps artifacts independently creatable, removes hard PRD/exploration prerequisite assumptions from skills, and replaces fixed lane-order stale invalidation with graph-based invalidation driven by actual declared sources.

## Decisions Made

- Store machine-readable artifact dependencies in `status.yml`, under an `artifacts` graph keyed by lane.
- Keep artifact frontmatter `source` as display-only/backward-compatible context.
- Do not add new `sources` frontmatter going forward.
- Make stale invalidation transitive across the `status.yml.artifacts` graph.
- Keep the command name `weave change progress`.
- Extend progress with repeatable source flags, for example `weave change progress architecture --source prd --source codebase --json`.
- Accepted source IDs for v1 are `exploration`, `prd`, `architecture`, `discussion`, `sessions`, and `codebase`.
- Validate sources and reject unknown source IDs.
- If progress is called without sources, record progress with no dependencies and include a visible note.
- Default `issues` progress to depend on `architecture` when architecture exists and no explicit source was passed.
- Do not add a `tech-debt` change type in this change.

## Options Considered

- Artifact frontmatter `sources` list: initially captured in exploration and PRD, but superseded by the decision to centralize the graph in `status.yml`.
- Rename `weave change progress`: rejected to preserve the existing command surface while changing its lifecycle semantics.

## Rejected Approaches

- Continue deriving stale state from fixed lane order.
- Treat direct `architecture.md` as proof that PRD and exploration were reached.
- Require PRD for fixes, refactors, docs, tests, CI, chores, or future tech-debt style work.
- Use filenames such as `prd.md` as canonical source IDs in the graph. The graph should use artifact IDs such as `prd`.

## User Preferences

- Bug fixes, refactors, and tech debt should be able to start with architecture or issues.
- The full pipeline is still valid for features, but should be guidance rather than a hard universal prerequisite chain.
- PRD and architecture skills should interview when context is insufficient instead of forcing an upstream artifact.
- Source-aware status should make stale warnings meaningful and avoid invalidating artifacts that did not actually depend on the changed source.

## Agent Recommendations

- Implement the graph in `src/lib/changes.ts` first, then update skills and tests around the new CLI behavior.
- Preserve the existing `stale` shape to minimize compatibility risk.
- Keep `stage` as rough orientation, but stop using artifact existence to imply skipped upstream lanes.
- Update installed skill copies and templates together, because tests validate shipped templates.
- Add focused lifecycle tests before broad docs cleanup.

## Unresolved Points

- Whether old artifacts that already have `sources` frontmatter should be normalized by this change or left as harmless historical metadata.
- Exact text for the no-source progress warning.
- Whether `weave-next` should recommend PRD for all `feat` changes or only when product behavior remains uncertain.
