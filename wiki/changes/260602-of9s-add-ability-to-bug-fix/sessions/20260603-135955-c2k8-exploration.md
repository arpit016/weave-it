# Session Capture: Exploration - 2026-06-03

## Summary

Re-explored the active-change side of the bug-fix workflow to generalize how `weave-issues` shapes `tasks.md`. Prior sessions only specified a `QA Findings` (`QF#`) section for bugs found during an active change. This session broadened that: within an active change the in-flight work can be more than QA bugs (for example a refactor), and `weave-issues` should record each kind of discovered work in the right categorized section of `tasks.md`.

The model was deliberately kept narrow for v1. Section selection is driven by the category of each discovered work item, not by the change's declared `type`. `T#` implementation tasks remain the backbone. Only two dedicated observation sections are supported: `QA Findings` (`QF#`) and `Refactors` (`R#`). Everything else stays a normal `T#` task, optionally tagged.

## Decisions Made

- Section selection is driven by the category of each discovered work item, not by the change's declared `status.yml.type` (Model B). `T#` stays the implementation backbone.
- Supported dedicated `tasks.md` sections are `QA Findings` (`QF#`) and `Refactors` (`R#`). All other in-flight work (chore, perf, docs, tech-debt) stays a normal `T#` task, optionally tagged.
- Refactors are modeled observation-style, mirroring QA findings: an `R#` entry records why/what and links to the `T#` task(s) that carry it out, and can be logged-but-deferred without a task yet.
- `tasks.md` layout is flat sibling sections: `Active Task Index` (+ `T#` details), then `QA Findings`, then `Refactors`. No umbrella heading.
- No special refactor routing or escalation guidance: record the `R#` and let the user decide whether to escalate or split it out.
- The `QA Findings` (`QF#`) shape is finalized in this session so `QF#` and `R#` are designed symmetrically (this resolves the prior open question about the exact `QA Findings` shape).
- Refactor status vocabulary is distinct from task and finding statuses: `proposed`, `accepted`, `deferred`, `done`, `out_of_scope`, `invalid`.
- `T#` tasks gain optional `Origin:` (`qa_finding` | `refactor`) and `Related finding:` (`QF#`/`R#`) fields so backbone tasks link back to their source observation.

## Options Considered

- Model A: the change's declared `type` reshapes the entire `tasks.md` template.
- Model B: the category of each discovered work item drives sections, regardless of change type.
- Both A and B combined (type sets a base template, discovered items add categorized sections).
- Category scope: just bugs + refactors; bugs + refactors + a generic catch-all; a broad fixed taxonomy; or open-ended agent-chosen categories.
- Refactor shape: observation-style `R#`; task-style tagged `T#`; or both depending on size.
- Layout: flat siblings; grouped under an umbrella `Discovered Work` heading; or flat plus a combined top index table.
- Refactor routing: both guards (behavior-change redirect + split large refactors out); behavior-change guard only; or no special routing.

## Rejected Approaches

- Model A and the combined model were rejected because the motivation centers on what the work is inside an active change, not the change's overall type; overall type is already handled upstream by `weave-architect`/`weave-prd`.
- A broader fixed taxonomy and open-ended categories were rejected for v1 because a sprawling taxonomy tends to rot; non-bug, non-refactor work is fine as a tagged `T#` task.
- Task-style-only refactors were rejected because the user wants discovered work kept distinct and traceable rather than blended into planned `T#` tasks, and wants to support note-it-now / do-it-later.
- The umbrella `Discovered Work` heading and the combined index table were rejected in favor of flat sibling sections.
- Refactor routing/escalation guards were rejected for v1; escalation is left to the user.

## User Preferences

- Wants `weave-issues` to reliably place the right sections in `tasks.md` for the kind of in-flight work, not just QA bugs.
- Wants discovered work kept visually and structurally distinct from planned implementation tasks.
- Prefers a small, concrete v1 scope (bugs + refactors) over a broad taxonomy.
- Prefers observation-style records that can be logged but deferred.
- Prefers a simple flat layout and minimal routing ceremony.
