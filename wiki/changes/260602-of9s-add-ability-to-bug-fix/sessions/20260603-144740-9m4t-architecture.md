# Session Capture: Architecture - 2026-06-03

## Summary

Produced the initial engineering design for the categorized `tasks.md` change and created `architecture.md` from the approved Plan Mode `weave-architect` discussion, the PRD, and codebase review.

The change is skill-content and test surface only: extend the canonical `weave-issues` template to add a classification step and two flat sibling sections (`QA Findings` / `QF#` and `Refactors` / `R#`) to the `<tasks-template>` block, propagate byte-identical installed copies via the CLI, and update the skill contract tests. No CLI/runtime code, no new lifecycle lane, and no new source IDs are required.

## Decisions Made

- `tasks.md` section selection is driven by work-item category, not change type; `T#` stays the backbone.
- Add `QA Findings` (`QF#`) and `Refactors` (`R#`) as flat siblings, both defaulting to `None.` like the existing `Invalid Tasks` section, for stable structure.
- Reuse the existing `issues` lane and source IDs; no new lane, source ID, or artifact type.
- Propagate template edits with `weave skill reset weave-issues --agent all` to force-write installed copies and refresh `.weave/agents.yml` hashes.
- Append-first, preview-before-write, and stable-ID reconciliation extend to `QF#` and `R#` with independent ID namespaces; a deferred `R#` may exist without a `T#`.
- `T#` tasks gain optional `Origin` and `Related finding` fields linking back to `QF#`/`R#`.

## Options Considered

- Always-present sections with `None.` defaults vs conditional sections that appear only when populated.
- Propagation via `weave skill reset` vs `weave skill update` vs hand-editing installed copies.
- Modeling categories as `T#` `Origin` tags only vs dedicated `QF#`/`R#` sections.
- Optional tweak of the frontmatter `description` to mention findings/refactors.

## Rejected Approaches

- Conditional sections were rejected for v1 in favor of stable always-present structure consistent with `Invalid Tasks`.
- Hand-editing installed copies was rejected as drift-prone and bypassing the manifest hash flow.
- `Origin`-tag-only modeling (no dedicated sections) was rejected because discovered work must stay distinct from planned tasks.
- A change-type-driven template (Model A) was already rejected during exploration.

## User Preferences

- Wants discovered work kept distinct and traceable, not blended into planned `T#` tasks.
- Prefers a small, concrete v1 scope (bugs + refactors) and minimal routing ceremony.
- Approved the architecture plan as presented.
