# Session Capture: Exploration - 2026-06-02

## Summary

Promoted the bug-fix workflow decisions from the two prior exploration session notes into the live exploration artifact.

The product direction is to support two bug workflows:

- Active-change QA bugs stay inside the active change and are tracked through `tasks.md` QA findings.
- Bugs reported after release or after time has passed become standalone `fix` changes that start from current truth, not old feature artifacts.

The latest discussion also clarified that standalone `fix` changes should not scaffold `exploration.md` by default. They should start with `status.yml`, `sessions/`, and `stage: started`, then create the first real artifact through the skill that fits the work.

## Decisions Made

- Active QA bugs remain in the active change.
- `weave-issues` owns active-change QA finding intake in `tasks.md`.
- Post-release or old-context bugs become new standalone changes with `type: fix`.
- Old feature/change artifacts are provenance only; current knowledge, current code, current tests, and recent changes are authoritative inputs.
- RCA, investigation, diagnosis, affected systems, and fix strategy live in `architecture.md`.
- `weave-architect` handles fix-type RCA/investigation in v1; no separate `weave-investigate` skill.
- `weave-next` should route fix changes toward `weave-architect`, `weave-issues`, or product artifacts depending on bug clarity and expected-behavior ambiguity.
- `weave-knowledge` closes the fix by recording updated current-state knowledge or a no-impact rationale.
- `weave change new --type fix` should not create `exploration.md` by default.
- Non-feature changes that do not create an initial live artifact should start with `stage: started`.

## Options Considered

- Keep creating `exploration.md` for every change type.
- Add an `intake` stage.
- Use alternative initial stage names such as `opened`, `created`, `active`, or `pending`.
- Add a separate `weave-investigate` skill for bug diagnosis.
- Add subchanges for active QA bugs.

## Rejected Approaches

- Creating scaffold-only `exploration.md` for fixes was rejected because it implies product discovery is the first artifact and makes `stage: exploration` look like real progress.
- `stage: intake` was rejected as too support-ticket flavored.
- `stage: active` was rejected as too vague.
- `stage: pending` was rejected because it implies waiting or blocking.
- A standalone `weave-investigate` skill was rejected for v1 because investigation/RCA naturally belongs in the architecture lane.
- Subchanges were rejected for v1 because active QA bugs can be handled inside `tasks.md` without adding parent-child lifecycle complexity.

## User Preferences

- The user wants active bugs and old bugs to have distinct, easy-to-explain flows.
- The user wants bug-related artifacts to avoid unnecessary product ceremony.
- The user wants old bugs to start from current reality instead of reopening stale historical artifacts.
- The user prefers `weave-architect` for RCA/investigation rather than a new skill.
- The user prefers `stage: started` for changes that exist but have not reached an artifact lane.

## Agent Recommendations

- Update `weave-issues` so `tasks.md` can include a `QA Findings` section with stable `QF#` IDs linked to implementation `T#` tasks.
- Update `weave-architect` so `type: fix` uses a lightweight RCA/investigation/fix-strategy structure.
- Update `weave-next` so `type: fix` does not treat missing or scaffold-only exploration as a blocker.
- Update `weave-new` and change creation behavior so fix changes scaffold only `status.yml` and `sessions/`, with no current artifact context.
- Add `stage: started` as a non-artifact initial state for fix-style changes.
- Keep `weave change progress <lane>` limited to real artifact lanes.
- Update README examples and skill contract tests for active QA findings, post-release fix flow, and `stage: started`.

## Unresolved Points

- Whether `started` should apply only to `fix` or also to `refactor`, `docs`, `test`, `ci`, and `chore`.
- Exact `tasks.md` QA Findings section shape.
- Exact fix-oriented `architecture.md` section template.
- Whether docs should include separate CS-, PM-, and QA-reported bug examples.
