# Session Capture: Exploration - 2026-06-02

## Summary

Explored how Weave should handle bug fixes and adjacent technical work without forcing every case through the full exploration -> PRD -> architecture -> issues pipeline.

The discussion split bug fixes into two broad cases:

- Active-change QA bugs found while a feature or change is still in development.
- Later bugs found after release or after enough time has passed that current behavior, code, and knowledge may have changed.

The active-change bug path was mostly resolved. Active QA bugs should stay inside the active change instead of creating a separate fix change or subchange. The existing `tasks.md` local implementation ledger should be extended to support QA findings.

## Decisions Made

- Active QA bugs remain in the active change.
- `weave-issues` should own active-change QA bug intake because it owns `tasks.md` generation and reconciliation.
- `tasks.md` should get a dedicated `QA Findings` section rather than mixing all bugs directly into normal implementation tasks.
- QA findings should have stable IDs such as `QF1`, `QF2`, separate from implementation task IDs such as `T1`, `T2`.
- Implementation work should remain normal `T#` tasks and link back to related `QF#` findings when needed.
- QA findings should be append-first. Agents should not casually rewrite earlier tasks or QA finding details.
- If a QA bug changes product scope, requirements, expected behavior, or acceptance criteria, the user should use the relevant artifact skill rather than letting `weave-issues` silently rewrite upstream artifacts.
- If a QA bug changes technical approach, affected systems, rollout, risk, testing, or architecture, the user should use `weave-clarify architecture` or `weave-architect`.
- `weave-capture session <lane>` remains the right tool when the discussion is useful but not ready to update a live artifact.

## Options Considered

- Always create a new change for every bug.
- Add a child/subchange model under active changes.
- Keep active QA bugs as ordinary tasks only, using an `Origin: qa_bug` field.
- Add a dedicated `QA Findings` section inside `tasks.md`.
- Add a separate skill such as `weave-qa`, `weave-bug`, or `weave-finding`.

## Rejected Approaches

- Always creating standalone bug changes for active QA bugs was rejected because it fragments an in-flight feature before the feature has landed as current product truth.
- A formal subchange or child-change model was rejected for v1 because it would add hierarchy, parent-child lifecycle behavior, branch questions, and stale propagation complexity.
- Using only an `Origin: qa_bug` field on normal tasks was considered useful but less clear than separating QA observations from engineering tasks.
- A new dedicated QA/bug skill was deferred. It may become useful later, but `weave-issues` is the simplest v1 owner because the data lives in `tasks.md`.

## User Preferences

- The user wants to close and simplify the active-change bug path first before solving old/post-release bugs.
- The user prefers a natural instruction flow where they can ask the agent to add a bug to `tasks.md`.
- The user wants bugs found during active QA to be identifiable as bugs or QA findings, not silently blended into planned task history.
- The user is concerned that AI might modify earlier tasks incorrectly, so preservation and append-first rules matter.
- The user agrees that artifact-specific changes should stay owned by the existing artifact skills.

## Agent Recommendations

- Extend the `weave-issues` skill contract so it can classify QA bug intake and append a `QA Findings` section in `tasks.md`.
- Use a shape like:
  - `## QA Findings`
  - QA finding index table with `ID`, `Status`, `Severity`, `Source`, `Related Task`, and `Summary`
  - Detailed `## QF#: <Summary>` sections with observed behavior, expected behavior, reproduction, artifact impact, and related task links
- Use QA finding statuses such as `new`, `accepted`, `fixed`, `verified`, `duplicate`, `not_reproducible`, `out_of_scope`, and `invalid`.
- Keep normal implementation work in `T#` tasks with optional fields such as `Origin: qa_finding` and `QA finding: QF#`.
- Add routing guidance:
  - implementation-only bug -> `weave-issues`
  - product behavior or acceptance change -> `weave-clarify prd` or `weave-explore`
  - technical design change -> `weave-clarify architecture` or `weave-architect`
  - useful discussion not ready for artifact update -> `weave-capture session <lane>`
- Require reconciliation previews before modifying existing task bodies, statuses, checked acceptance criteria, or invalidating tasks.

## Unresolved Points

- The post-release or old-context bug path still needs exploration.
- Need decide whether standalone old bugs should always use `--type fix` changes or whether some should be captured as chores/refactors depending on impact.
- Need decide how strongly `weave-next` should route old-context fixes toward current knowledge, code, architecture, or tasks.
- Need decide whether the active-change `QA Findings` structure should be added only to `weave-issues` guidance or also to README examples and tests.
- Need decide whether a future `weave-qa` alias is worth adding after the `weave-issues` path proves itself.
