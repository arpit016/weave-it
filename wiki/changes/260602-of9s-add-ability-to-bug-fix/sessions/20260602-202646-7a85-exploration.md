# Session Capture: Exploration - 2026-06-02

## Summary

Continued exploration of the bug-fix workflow, focusing on bugs reported months after the original feature or change shipped.

The post-release or old-context bug path was locked as a separate workflow from active-change QA bugs. Old bugs should not reopen the original feature change as the working context. Instead, users should create a new standalone `fix` change and use current knowledge, current code, current tests, and relevant historical context as inputs.

## Decisions Made

- Bugs reported after time has passed should become new standalone changes with `type: fix`.
- The old feature/change artifacts should be treated as provenance only, not as current truth or the active work context.
- Root cause analysis, investigation notes, diagnosis, affected systems, and fix strategy should live in `architecture.md`.
- `weave-architect` should own post-release bug investigation/RCA in v1.
- No separate `weave-investigate` skill should be added in v1.
- `weave-architect` should adapt its output when the active change has `status.yml.type: fix`.
- For fix-type changes, `architecture.md` may be a lightweight diagnosis and fix-strategy artifact, not a full feature architecture document.
- If root cause is unknown, `weave-architect` can create an investigation-first architecture with symptoms, hypotheses, investigation plan, likely affected systems, and open technical questions.
- Once root cause is found later, users should run `weave-clarify architecture` to update the RCA and fix strategy.
- Implementation task breakdown remains owned by `weave-issues`.
- Product behavior or acceptance changes should use `weave-prd` or `weave-explore` only when the bug exposes ambiguity or changes expected behavior.
- After implementation, `weave-knowledge` should record whether current-state behavior changed or whether there was no durable knowledge impact.

## Options Considered

- Add a separate skill such as `weave-investigate`.
- Keep investigation/RCA inside `weave-architect`.
- Skip architecture entirely for all post-release bugs.
- Use `weave-prd` or `weave-explore` as the default starting point for old bugs.

## Rejected Approaches

- A separate `weave-investigate` skill was rejected for v1 because it would make users decide between investigation and architecture even though both would update the architecture lane.
- Reopening the old feature change was rejected because current behavior, code, tests, and knowledge may have changed since the original work shipped.
- Making PRD/exploration the default old-bug path was rejected because most old bugs need technical diagnosis or implementation tasks, not full product discovery.
- Skipping architecture for every bug was rejected because many production bugs need an RCA, risk analysis, investigation plan, or fix strategy worth preserving.

## User Preferences

- The user wants the post-release bug flow to be concise and easy to explain through existing skills.
- The user wants RCA to have a clear artifact home.
- The user prefers using `weave-architect` rather than introducing a new skill unless the workflow later proves it needs one.
- The user expects `weave-architect` to infer the bug/RCA template from `status.yml.type: fix` and bug-oriented prompt language.

## Agent Recommendations

- Update `weave-architect` guidance so `type: fix` changes use a fix-oriented template with sections such as:
  - Bug Context
  - Observed Behavior
  - Expected Behavior
  - Reproduction
  - Root Cause Analysis
  - Investigation Plan, when RCA is unknown
  - Affected Systems
  - Fix Strategy
  - Regression Tests
  - Risks And Rollout
  - Open Technical Questions
- Update `weave-next` guidance so fix changes are routed toward `weave-architect` when diagnosis is needed, `weave-issues` when the bug and fix are obvious, and `weave-prd` or `weave-explore` only when expected behavior is unclear.
- Document the normal post-release bug flow as:
  - `weave-new "Fix <bug>" --type fix`
  - `weave-architect "Investigate this bug: observed..., expected..., repro..., logs..."`
  - `weave-issues`
  - `weave-knowledge`
- Allow users who already know the RCA to ask `weave-architect` to capture the RCA and fix approach directly.

## Unresolved Points

- Need decide exact wording and section shape for the fix-oriented `architecture.md` template.
- Need decide whether old bug reports should get a dedicated `Bug Report` section in `tasks.md`, `architecture.md`, or both.
- Need decide whether `weave-new` guidance should explicitly suggest `--type fix` for support, PM, QA, or production bug reports.
- Need decide whether documentation should include examples for support-reported, PM-reported, and QA-reported old bugs.
