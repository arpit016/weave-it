# Session Capture: Exploration - 2026-06-02

## Summary

Explored the desired product behavior for changing `weave-issues` from an external issue-tracker publishing flow into a local `tasks.md` generation and reconciliation flow.

The active change is `260602-943x-fix-issues-skill-with-creating-tasks`. Current repository context showed that `tasks.md` is already the local artifact used as issue-breakdown evidence, while `issues` is a lifecycle lane rather than an artifact context.

## Decisions Made

- Keep `tasks.md` as the local file for issue/task breakdowns. Do not introduce `issues.md`.
- Keep the skill name and lifecycle lane as `weave-issues` / `issues`.
- Make `weave-issues` local-only for now. It should not publish to external issue trackers.
- `weave-issues` should create the initial task breakdown, but should not become the day-to-day task status updater.
- When `tasks.md` already exists, `weave-issues` should read current tasks and current source artifacts, then decide whether to update, refresh, add, or remove task content.
- Preserve existing task progress when prior tasks still map cleanly to the refreshed breakdown.
- Always preview proposed `tasks.md` changes and wait for explicit user approval before writing.
- Use `invalid` as the status for tasks that no longer apply after source artifacts change, instead of deleting them.

## Options Considered

- Rename the local artifact to `issues.md`.
- Support both `tasks.md` and `issues.md`.
- Keep external tracker publishing as an optional mode.
- Make `weave-issues` maintain full local task status over time.
- Refuse to run when `tasks.md` already exists.
- Append refreshed breakdowns instead of reconciling the current tracker.
- Reset task statuses and checkboxes during regeneration.
- Delete obsolete tasks.

## Rejected Approaches

- `issues.md` was rejected because existing lifecycle detection, docs, and prior architecture decisions already treat `tasks.md` as local issue-breakdown evidence.
- Optional external publishing was rejected for this change to keep the workflow local-only.
- Full local-board behavior was rejected as too heavy for the current scope.
- Clean regeneration was rejected because it could discard useful local progress.
- Deleting obsolete tasks was rejected because preserving an `invalid` record is more useful for local history.

## User Preferences

- Prefer local issue/task tracking in `tasks.md`.
- Prefer local-only operation over external tracker publishing for now.
- Prefer generated breakdowns over ongoing status-management behavior.
- Prefer intelligent reconciliation on rerun instead of blunt replacement.
- Prefer preserving progress.
- Prefer preview-and-approve before writing.
- Prefer `invalid` as the status for obsolete tasks.

## Agent Recommendations

- Update the canonical `weave-issues` skill and installed copies to replace tracker publishing with local `tasks.md` writing after approval.
- Keep `tasks.md` frontmatter as `artifact: tasks` and include status legend, task index, task sections, blockers, acceptance criteria, and verification notes.
- Keep `weave change progress issues --source architecture --json` after successful local task creation or reconciliation when architecture is the source.
- Update docs and tests so `weave-issues` is described as creating and reconciling local `tasks.md`.

## Unresolved Points

- The user may have additional concerns about `weave-issues` beyond the local `tasks.md` behavior.
- Exact wording and section order for the revised skill can be finalized during implementation.
