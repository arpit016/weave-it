# Session Capture: Architecture - 2026-06-02

## Summary

Created the initial architecture for the `weave-issues` local `tasks.md` workflow. The design keeps the implementation as a skill/template/docs/test update and avoids adding a compiled task generator, `issues.md`, or new lifecycle source IDs.

## Decisions Made

- Implement the change through `weave-issues` skill instructions and shipped documentation surfaces.
- Update canonical and installed skill copies together.
- Keep the existing lifecycle runtime unchanged.
- Use only existing lifecycle source IDs for `weave change progress issues`.
- Record concrete external issue references and local paths in `tasks.md` source context.
- Define a canonical `tasks.md` shape.
- Treat `not_tested` as implementer-applied status vocabulary.

## Options Considered

- Add a compiled task generator.
- Add lifecycle source IDs for external/local references.
- Keep tracker publishing as an optional output.
- Introduce `issues.md`.
- Leave `tasks.md` formatting mostly flexible.

## Rejected Approaches

- Compiled generation was rejected as larger than the PRD scope.
- New lifecycle source IDs were rejected because external references do not have Weave stale-invalidation semantics.
- Tracker publishing was rejected because this change is local-output only.
- `issues.md` was rejected because `tasks.md` is existing local issue evidence.
- Loose `tasks.md` formatting was rejected in favor of a canonical shape for consistency.

## User Preferences

- Prefer skill/templates only.
- Prefer keeping existing lifecycle source IDs.
- Prefer a canonical `tasks.md` shape.

## Agent Recommendations

- Move next to implementation issue breakdown with `weave-issues`, or implement the template/docs/test changes directly if the architecture is accepted.
- Keep implementation scoped to skill content and tests.
