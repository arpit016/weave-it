# Session Capture: Exploration - 2026-06-02

## Summary

Continued exploring `weave-issues` behavior for repositories that do not have an existing automated test suite. The discussion clarified that the skill should preserve vertical-slice thinking without requiring strict TDD or blocking task generation when automated tests are unavailable.

The active change remains `260602-943x-fix-issues-skill-with-creating-tasks`.

## Decisions Made

- `weave-issues` should not treat missing automated tests as a hard blocker for generating local `tasks.md`.
- `weave-issues` should inspect the target repo for existing test infrastructure before drafting tasks.
- If a usable test base exists, code-affecting vertical slices should include relevant automated test expectations and verification commands.
- If no usable test base exists, generated tasks should include explicit manual or smoke verification expectations.
- `weave-issues` should frame this as vertical-slice completeness, not strict test-first TDD.
- `not_tested` should be task-tracking vocabulary, but `weave-issues` should not assign it to newly generated tasks.
- Implementers, not `weave-issues`, should apply `not_tested` later when implementation appears complete but automated verification could not be completed.
- Newly generated tasks should still start as `todo` unless another real blocker is known.

## Options Considered

- Always create an early test-harness setup task when no test suite exists.
- Mark missing tests as HITL or blocked before generating task breakdowns.
- Require true test-first/TDD instructions in every task.
- Set generated tasks to `not_tested` when the repo lacks automated tests.
- Omit `not_tested` from the local task vocabulary entirely.

## Rejected Approaches

- Mandatory test-harness setup was rejected because it can expand scope when the source plan did not ask for it.
- Hard blocking on missing tests was rejected because small repos, docs work, fixes, and chores may still need actionable local tasks.
- True TDD wording was rejected in favor of the broader vertical-slice rule.
- Assigning `not_tested` during task generation was rejected because verification status is only known during implementation.
- Omitting `not_tested` entirely was rejected because implementation agents need a visible way to record completed-but-unverified work.

## User Preferences

- Prefer vertical-slice completeness over strict TDD process language.
- Prefer using automated tests when the repo already has a usable testing base.
- Prefer manual or smoke verification fallback when the repo does not have test infrastructure.
- Prefer `not_tested` as a visible local task status.
- Prefer `weave-issues` to define status vocabulary and verification expectations, while implementers update actual status after execution.

## Agent Recommendations

- Update `weave-issues` instructions so codebase exploration includes detecting available test commands, test folders, and established testing conventions.
- Add `not_tested` to the `tasks.md` status legend with wording like: implementation appears complete, but automated verification could not be completed.
- Keep generated task statuses as `todo` by default.
- Add per-task Verification guidance that records automated tests, manual checks, smoke checks, or reasons automated tests are unavailable.
- Avoid language that implies `weave-issues` can know execution-time verification outcomes.
