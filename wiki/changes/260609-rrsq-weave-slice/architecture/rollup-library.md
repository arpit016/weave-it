# Rollup Library

## Overview

Single shared library at `src/lib/sliceRollup.ts` is the source of truth for all derived slice state. Every Weave skill that writes primary state calls it inline. A `weave slice rollup` CLI exposes the same library for non-skill writers (manual editor edits, post-merge resolutions, CI checks).

No editor PostToolUse hooks. No `.claude/hooks.json` or Cursor harness configs. The design is harness-agnostic.

## Why Writer-Derives Instead Of Editor Hooks

PostToolUse hooks (Claude Code, Cursor harness) tie derivation to one specific agent harness. Weave targets multiple harnesses (Claude Code, Cursor, Codex, Opencode, raw editors). Alternatives considered:

- Per-harness configs — rejected; N configs to ship and test.
- Filesystem watcher daemon — rejected; process-management overhead.
- Writer-derives — chosen. Weave skills are the primary writers in the agent-driven happy path; calling the library inline eliminates the hook abstraction while preserving a defensive parser and auto-stage of derived files.

Tradeoff: manual edits made outside any Weave skill leave derived state stale until the next Weave skill invocation or manual `weave slice rollup`. Acceptable because skills are the dominant writers.

## Trigger Granularity: Batched

The library runs once per logical write episode, not after every individual `tasks.md` write. Episode boundaries that trigger rollup:

1. End of a `weave-execute` episode (all selected tasks completed).
2. Before any HITL pause in `weave-execute` (so the human sees fresh state).
3. Before any error exit in `weave-execute`.
4. After `weave-slices` or `weave-fix` finishes scaffolding new slices.
5. Manual `weave slice rollup` invocation (humans, pre-commit hooks, CI).

Per-task writes during a `weave-execute` run do not trigger rollup individually. Intermediate views of `status.yml.task_summary` may be stale mid-run; they reconverge at the next episode boundary.

## Per-Call Behavior

- Parse the affected slice's `tasks.md` defensively: only update counters when their section headers parse cleanly; leave previous values otherwise.
- Rewrite `<slice>/status.yml.task_summary` (`total`, `done`, `blocked` counts).
- Re-derive slice `status` from task states (mechanical rules in `slice-model.md`).
- Regenerate `task-slices/dependency-graph.md` from all slice `status.yml` files (always; only when slice count >= 2). Unconditional regen — the file is a pure deterministic function of `{id, title, status, depends_on, owner}` across all slices.
- `git add` the touched derived files so they never block a subsequent commit.
- Cycle detection in `depends_on`: the primary write still succeeds; `dependency-graph.md` shows `WARNING: dependency cycle detected, graph not regenerated` until the cycle is resolved.

## CLI Surface

```text
weave slice rollup [--slice <path>] [--all] [--check]
```

- `--slice <path>`: rollup a single slice's derived state.
- `--all` (default): rollup every slice in the active change + regenerate `dependency-graph.md`.
- `--check`: dry-run mode; exits non-zero if derived files would change. Intended for users wiring pre-commit / husky / CI on their own.

## Dependency Graph Structure

`task-slices/dependency-graph.md` sections, in order:

1. **Purpose** — one-liner about source of truth.
2. **Graph** — ASCII tree (multi-parent slices duplicated under each parent).
3. **Slice dependencies** — table `| Slice | Depends on | Status | Owner |`. Status column renders `ready`/`blocked` for `pending` slices based on dep state.
4. **Ready to work now** — `pending` slices whose deps are all `done`.
5. **Blocked slices** — `pending` slices with at least one unfinished dep, listing the blockers.
6. **Critical path** — longest dep chain by node count (tiebreak on slice numeric prefix).
7. **Parallel work** — narrative naming the largest parallel group off the critical path.

Banner at top: `AUTO-GENERATED by weave slice rollup. Do not edit by hand. Source of truth: per-slice status.yml.`

## Pre-Commit Hook Installer

Not shipped in v1. Teams that want auto-derivation on every commit can wire `weave slice rollup --check` (or `weave slice rollup`) into pre-commit, husky, lint-staged, or CI on their own. Non-skill writes recover on the next Weave skill invocation. Revisit if drift becomes a real pain point.

## Call Sites

Writers that invoke the rollup library:

- `weave-execute` — at episode boundaries (see Trigger Granularity above).
- `weave-slices` — after scaffolding new or expanded slice folders.
- `weave-fix` — after scaffolding the initial single slice.
- `weave slice rollup` CLI — manual invocation by humans or CI.
