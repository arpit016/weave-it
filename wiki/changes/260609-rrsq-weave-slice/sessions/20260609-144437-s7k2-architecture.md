# Session Capture: Architecture - 2026-06-09

## Summary

Long working session that started from the problem of multi-engineer collaboration on a single Weave change and converged on a new artifact model: per-change `task-slices/` folders. Compared Weave's existing flat `tasks.md` model against other assembly-line-style task plans, established that markdown + git has an inherent collision ceiling, and arrived at a slice-folder design that segments the work by vertical user-behavior bullet while keeping internal task ownership granular.

Also nailed down posture on external tracker integration (MCP via agent, no Weave-side provider code) and the deprecation path from the current `weave-issues` skill to a new `weave-slices` skill.

## Decisions Made

- Adopt a per-change `task-slices/<NN>-<slug>/` folder model with four files per slice:
    - `slice.md` - human narrative (Outcome / User flow / In scope / Out of scope / Acceptance criteria). No frontmatter. Pure markdown.
    - `contracts.md` - FE/BE handshake for this slice (API shape, error responses, UI states, event payloads, validation rules).
    - `tasks.md` - task list with stable `T#` IDs, grouped under per-repo headings (and an optional `## cross-cutting` heading), plus existing `## QA Findings` and `## Refactors` sections at the bottom.
    - `status.yml` - machine-readable tracker (`id`, `title`, `status`, `owner`, `repos`, `depends_on`, `task_summary`, `updated_at`).
- Use the slice as the unit of vertical (tracer-bullet) work; allow horizontal sub-tasks inside each slice. This resolves the "T# is both vertical and horizontal" conflation in the current `tasks.md`.
- `slice.md` carries only human-readable content. `status.yml` carries all machine-readable state. Do not fold them together.
- Keep stable `T#` task IDs (`T1`, `T2`, ...) so cross-task references (`Blocks: T3`, `Related Task: T1`) remain unambiguous. Do not use prose references like "Blocks: frontend integration".
- Every task carries an explicit `Repos: <name1>, <name2>` field listing the repo names it touches (single repo for most tasks, multi for cross-cutting). Repo values are workspace repo IDs from `workspace.yml.repos[].id`.
- Group tasks under `## <repo-name>` headings for human scanning. Headings are presentational; `Repos:` on each task is the source of truth.
- Cross-repo tasks live under a `## cross-cutting` heading with an explicit multi-value `Repos:` line.
- Tasks include a mandatory `Files:` list with `(C)` create / `(M)` modify / `(D)` delete tags. The list is documentation for engineers and reviewers, not an input to programmatic role/repo derivation.
- Owners are free-text strings only - no team registry, no auto-resolution. `Owner: Stephen` on a task, `owner: sharma` (singular) on a slice `status.yml`. The agent can edit these conversationally on request; no `team.yml` config file.
- `QA Findings` (`QF#`) and `Refactors` (`R#`) stay inside the slice's `tasks.md` using the existing Weave model - no separate `findings.md`.
- `task_summary` counts in `status.yml` are derived by re-parsing `tasks.md` after every write. Engineers never type these numbers. (Later revised to writer-derives + batched rollup; see session `20260609-174155-b5q2-architecture.md`.)
- Dependency graph between slices lives in each slice's `status.yml.depends_on: [<slice-id>, ...]`. Change-level `status.yml` is a derived rollup; engineers never hand-edit cross-slice state.
- Build a new `weave-slices` skill rather than modifying the existing `weave-issues`. Deprecate `weave-issues` later once `weave-slices` is stable. No silent breakage to any existing flow.
- External issue tracker integration (Linear / Jira / GitHub) will use MCP via the agent - not Weave-side provider clients. Weave provides link storage (`wiki/changes/<id>/links.yml`), task snapshots, and drift detection; the agent calls the appropriate MCP. No API tokens, no SDKs, no provider abstraction inside Weave.

## Options Considered

### Multi-engineer collaboration on one `tasks.md`

- A. Accept the residual git conflicts on a single shared `tasks.md`.
- B. Split changes by behavior slice (separate sub-changes) - initially considered, then absorbed into the slice-folder model.
- C. Move to a server-mediated store (database / Linear as truth) - rejected, betrays Weave's local-first contract.
- D. Add CLI-mediated writes + PostToolUse hook for derived counts - kept as hygiene, doesn't solve true concurrent edits.

### Branch model

- A. One branch per change in each repo (current). Kept for v1.
- B. One branch per task per repo. Rejected as overkill.
- C. Hybrid: per-task branches opt-in. Deferred.

### tasks.md structure

- A. Keep monolithic (current). Rejected for multi-slice changes.
- B. Index + per-task files. Rejected - too fragmented.
- C. Append-only event log + materialized view. Rejected - over-engineered.
- D. Slice folders, each with its own narrative + contracts + tasks + status. Chosen.

### Coordination state (who is doing what)

- A. In-file `Status:` / `Owner:` lines (current). Kept.
- B. `status.yml.execution.tasks[T#]` machine-readable block. Deferred - not needed in v1 given the slice folder split lowers contention.
- C. External tracker as coordination source. Deferred - MCP integration supports it later.
- D. Out-of-band coordinator service. Rejected.

### Roles vs repos for task grouping

- A. Role-based grouping (`api`, `dashboard`, `qa`) with a `team.yml` mapping paths to roles to default owners. Rejected - invents a parallel taxonomy alongside the existing `workspace.yml` repos.
- B. Repo-based grouping using `workspace.yml.repos[].id` directly. Chosen.

### Owner assignment

- A. Workspace-level `team.yml` with members and `repo_owners`. Rejected as unnecessary infrastructure.
- B. Free-text `Owner: <name>` typed by humans, with agent edits on request. Chosen.

### Bug surface (where in-flight bugs go)

- A. Separate `findings.md` per slice. Rejected - adds a file type, low collision benefit at slice scope.
- B. Keep `## QA Findings` and `## Refactors` inside the slice's `tasks.md` (existing Weave model). Chosen.

### External tracker integration approach

- A. Reference-only with no Weave code. Considered as a minimum baseline.
- B. Push-on-demand from Weave to tracker via provider plugins. Rejected in favor of D.
- C. Pull-on-demand from tracker into Weave. Same - deferred.
- D. MCP via agent, with Weave providing link storage + snapshots. Chosen.
- E. Tracker as truth, Weave as projection. Rejected.

### `T#` IDs in tasks

- A. Drop IDs, identify tasks by description. Rejected - breaks dependency and finding references.
- B. Keep stable `T#` IDs with checkbox-style task rows. Chosen.

### `slice.md` vs `status.yml` split

- A. Fold metadata into `slice.md` frontmatter, drop `status.yml`. Considered, then rejected.
- B. Keep `slice.md` as pure human narrative, `status.yml` as machine tracker. Chosen - clear separation of audience.

## Rejected Approaches

- Per-task branches (`change/<id>/T3-...`) - overkill for current scale.
- Sub-changes as separate change folders for FE-only and BE-only work - recognized as the horizontal-layer split anti-pattern that breaks tracer bullets.
- Splitting `tasks.md` per task into separate files - too fragmented for small benefit.
- Adding lock / claim / lease primitives for multi-agent task ownership - rejected as out of scope for Weave's local-first model.
- `team.yml` registry with members, roles, paths, default owners - added config without enough value to justify it.
- `Role:` field on tasks - replaced by `Repos:` because repos already exist in `workspace.yml`.
- Path-to-repo derivation algorithm for headings - replaced by explicit `Repos:` declarations written by the agent.
- Provider plugin abstraction for Linear / Jira / GitHub - replaced by MCP-via-agent.
- Webhook listening, two-way status sync, real-time tracker integration - out of scope.

## User Preferences

- Local-first, file-based, markdown-and-CLI. No service dependencies.
- Accept residual git conflicts on shared markdown files as the price of multi-engineer collaboration.
- Minimum new concepts; avoid parallel taxonomies (e.g., do not add roles when repos already exist).
- Conversational ownership/assignment is acceptable; structured registries are not required.
- Detailed artifacts (architecture + tasks) are the coordination mechanism, not elaborate state machines.
- New skill alongside existing for any non-trivial change; deprecate the old later once the new one is stable.
- No users currently, so migration cost of an existing flat `tasks.md` is not a blocker.
- Plan mode is preferred for design discussion before any code changes.

## Agent Recommendations

- Build `weave-slices` as the new skill that generates `task-slices/` folders from PRD + architecture. Replace the slice-generation path of `weave-issues`, leave the existing skill in place for now.
- Add a rollup mechanism that re-derives `status.yml.task_summary` from `tasks.md`. Use a defensive parser: do not overwrite valid counts when sections are missing in an in-progress write. (Later revised to writer-derives; see session `20260609-174155-b5q2-architecture.md`.)
- Extend `weave-next`, `weave-execute`, `weave-prepare` to understand slice IDs (`/weave-execute 03` or `/weave-execute 03 T2`). Reuse the existing change-branch model for v1.
- Keep `architecture/` at the change level for cross-cutting design (data model, auth, deployment). Move FE/BE handshake details into the relevant slice's `contracts.md`.
- For external integration, ship the link-storage primitives (`links.yml`, `weave issue link / list / snapshot / record-push`) and a `weave-sync-issues` skill that documents the agent + MCP workflow. Defer any HTTP/SDK code.
- Phase the rollout: (1) slice folder scaffolding + `weave-slices` skill; (2) `weave-execute` / `weave-prepare` slice awareness; (3) PostToolUse hook for `task_summary`; (4) deprecate `weave-issues`; (5) MCP-based external integration.
- Document the multi-engineer collaboration model and its residual git conflict cost in `wiki/knowledge/domains/change-workflow/` so future agents and contributors do not re-derive it.

## Unresolved Points

- Branching model for slices. Current decision: keep change-level branches. Whether and when to move to per-slice branches (each slice has its own branch and PR) is deferred.
- `Files:` validation. Should `weave-slices` enforce that every task has at least one `Files:` entry, or treat it as best-effort? Leaning enforce, not confirmed.
- `status.yml.repos` derivation. Should it be derived from the union of `Repos:` values in `tasks.md`, or maintained explicitly? Probably derived by the hook, but a lint check helps either way.
- Cross-cutting heading name. `## cross-cutting` is the working choice; worth confirming during the first real slice generation.
- `weave-next` behavior for slices. Should it surface the next ready slice (based on dep graph), the next ready task within a slice, or both?
- Hook implementation surface. Claude Code's PostToolUse hook is one mechanism; Cursor's agent harness is another. Whether to ship a Weave-native parser that reruns on `weave change progress` instead of (or in addition to) an editor hook is open.
- Deprecation timeline for `weave-issues`. No date set. Suggested trigger: when `weave-slices` has shipped, been used on at least one real change end-to-end, and verified against the new templates and skills.
