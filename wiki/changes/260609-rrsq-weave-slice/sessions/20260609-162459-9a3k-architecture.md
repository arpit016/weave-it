# Session Capture: Architecture - 2026-06-09 (Finalization)

## Summary

Second architectural working session for the task-slices model. Started from the first session's open question on the dependency-graph rollup and converged on a markdown-only design. Then layered in the bug-fix workflow (`weave-fix` skill + `findings.md` artifact), the AFK/HITL per-task field, slice-aware updates to `weave-next` and `weave-execute`, the deprecation of `weave-prepare` (functionality folded into `weave-execute`), and the hard rename of `weave-issues` to `weave-slices`. Backwards compatibility resolved as dual-mode skill dispatch (no migration tool, legacy flat `tasks.md` supported indefinitely). All design decisions for v1 are now locked; the plan file at `/Users/arpit/.cursor/plans/task-slices_model_c219422f.plan.md` captures execution detail.

## Decisions Made

### Dependency graph rollup

- Live at `wiki/changes/<id>/task-slices/dependency-graph.md`. Hook-generated, do-not-edit.
- Markdown-only (no companion YAML). Truth stays in per-slice `status.yml`; the agent reads slice files directly. The markdown is for humans and conversational agent surface.
- Hook regenerates the file on every slice `status.yml` write. Only generated when slice count >= 2.
- Sections: Purpose, Graph (ASCII tree with multi-parent duplication), Slice dependencies table (`| Slice | Depends on | Status | Owner |`), Ready to work now, Blocked slices, Critical path, Parallel work.
- ASCII tree chosen over Mermaid for renderer-agnosticism.

### Status vocabulary (slice level)

- Stored: `pending | in_progress | done` (3 values).
- Derived: `ready | blocked` (only appear in `dependency-graph.md`).
- Engineers never write `ready` / `blocked`. Hook computes them from `depends_on` + other slices' status.
- Slice `status` itself is also hook-derived from task states in the slice's `tasks.md`:
  - all tasks `done` -> slice `done`
  - any task `in_progress`, or some tasks `done` but not all -> slice `in_progress`
  - else -> slice `pending`
- Engineers do not manually set slice status; the only source of truth is per-task `Status:` in `tasks.md`.

### Task vocabulary (within a slice)

- Per-task fields: `T#`, `Status:`, `Owner:` (free text), `Repos:` (csv of repo names from `workspace.yml.repos[].id`), `Execution:` (`afk` | `hitl`, default `hitl`), `Blocked by:` (csv of `T#` IDs in this slice only), `Files:` with `(C)` / `(M)` / `(D)` tags, `Acceptance:`, `Verification:`.
- Task statuses keep today's richer vocab: `todo | in_progress | done | not_tested | blocked | invalid`.
- AFK / HITL classification IS the same concept as today's `weave-issues` `Type: HITL | AFK` field - just renamed and shifted from "leaf unit" (slice in old model) to "task" (in new model where slice is a container).
- Cross-slice task dependencies disallowed in v1. Only within-slice `Blocked by: T#`. Cross-slice coordination at slice level via `status.yml.depends_on`.

### Bug-fix workflow (`weave-fix` + `findings.md`)

- New `findings.md` artifact at change root, required for every `--type fix` change (even trivial typo fixes).
- Sections: Summary (required), Repro (optional), Scope & Impact (optional), Root cause (filled in as diagnosed), Related (external issue links / logs).
- New `weave-fix` skill (chat-driven, not CLI). Single-turn flow: derives slug, runs `weave new --type fix`, writes `findings.md` (Summary minimum), scaffolds single slice at `task-slices/01-<slug>/` with `tasks.md` + `status.yml` (skips `slice.md` / `contracts.md` for trivial fixes), reports next step.
- `weave-fix` always produces a slice folder, not a flat `tasks.md`. One mental model across all change types.
- Scope-growth path: idempotent `weave-slices` re-run. No `--expand` flag, no separate "promote" mode. Skill inspects current slices vs upstream artifacts and proposes additive expansion. Never silently moves `in_progress` or `done` tasks.
- No dedicated `weave-findings` skill. `weave-fix` creates + updates; `weave-clarify findings` handles ad-hoc edits.
- `findings` is a first-class lane in lifecycle: change-level `status.yml.artifacts.findings: { sources: [discussion, codebase], updated_at }`. CLI gets `weave change progress findings --source <list> --json`.

### Per-change-type lane chains

- `--type feat`: `exploration.md` -> `prd.md` -> `architecture/` -> `task-slices/`
- `--type fix`: `findings.md` -> `architecture/` (optional) -> `task-slices/`
- `--type chore` / `--type refactor`: `exploration.md` -> `architecture/` (optional) -> `task-slices/`

### Skill ecosystem updates

- `weave-execute`: dual-mode (detect `task-slices/` folder). Slice mode adds selectors (`/weave-execute <slice-id> <task-id>`), reads slice's `tasks.md`, branches on `Execution:` field (afk runs autonomously, hitl pauses at checkpoints). Absorbs branch-prep responsibility from the now-deprecated `weave-prepare` skill.
- `weave-next`: dual-mode. Slice mode walks `task-slices/*/status.yml`, computes ready set, suggests next slice + task. Biases toward critical-path slices when multiple are ready. Adds `/weave-next afk` filter for autonomous-eligible tasks across all ready slices.
- `weave-prepare`: deprecated entirely. Branch-prep folds into `weave-execute`. Deprecation banner added; skill removed after one release cycle. No CLI changes - today's `weave task prepare` is called internally by `weave-execute`.
- `weave-clarify`: gains `findings` lane.
- `weave-capture`: gains `findings` lane. Session notes for fix-type changes capture into `sessions/*-findings.md`.
- `weave-architect`: accepts `findings.md` as upstream source for fix-type changes (in addition to `prd.md`).
- `weave-issues` -> `weave-slices`: hard rename + full rewrite. No deprecation banner, no parallel skills. The `issues` artifact lane in lifecycle / CLI is also renamed to `slices`. After this change, `weave-issues` does not exist.

### Backwards compatibility

- Dual mode in skills. Detection: presence of `task-slices/` folder = slice mode; absence + presence of `tasks.md` = legacy flat mode; neither = no tasks yet.
- No migration tool. Older changes (including the meta-change `260609-rrsq-weave-slice` itself) stay flat indefinitely.
- No forced deprecation timeline for flat mode. Removal of flat-mode dispatch is out of scope here; happens in a future change when no legacy in-flight changes remain.

### Hook architecture

- PostToolUse hook (Claude Code + Cursor harness) with `weave slice rollup` CLI fallback.
- On `<slice>/tasks.md` write: re-parse tasks, rewrite `<slice>/status.yml.task_summary` + derive slice `status` from task states. Defensive parser: never overwrite valid counts when sections are missing in an in-progress write.
- On `<slice>/status.yml` write: regenerate `task-slices/dependency-graph.md`. Cycle detection: write succeeds but `dependency-graph.md` shows warning until cycle is resolved.

## Options Considered

### Dep graph rollup shape

- A. Lean YAML - graph + topo + waves only. Rejected.
- B. Full YAML - full per-slice rollup. Rejected.
- C. Full YAML + mermaid markdown. Rejected.
- D. Markdown-only (user-sketched), no YAML. Chosen. Closest to Weave's markdown-everywhere ethos; truth in per-slice `status.yml`; agent reads slice files directly.

### `waves` concept

- A. Persist `waves` in rollup (parallel groups derived by max-depth layering). Considered.
- B. Drop `waves`; rely on `topo_order` + dynamic `ready` set. Chosen implicitly when we switched to markdown-only - the "Parallel work" section in the markdown carries the narrative without needing a persisted `waves` list.

### Status vocabulary

- A. Stored 3 (`not_started | in_progress | done`) + derived 2 (`ready | blocked`). Chosen.
- B. Stored 3 (`pending | in_progress | done`) + derived 2. Same as A; we chose `pending` over `not_started` for naming.
- C. Stored 5 (all values stored). Rejected - too much state to maintain; risk of drift.

### Where bug reports live

- A. Skip top-level artifact for trivial fixes; description lives in slice's `tasks.md`. Considered.
- B. Introduce `bug.md` at change root for fix-type. Considered.
- C. Repurpose `findings.md` as dual-scope (initial bug report + accumulated QA findings). User-proposed and chosen, with `findings.md` always created for fix-type.
- D. Broaden `exploration.md` semantics to "change intent". Rejected - semantically dishonest.

### `weave-fix` shape

- Skill (chat-driven) vs CLI command vs hybrid. Chosen: skill.
- Always produce single slice folder vs flat `tasks.md` for trivial. Chosen: always slice folder. One mental model.

### Scope-growth path

- A. Idempotent `weave-slices` re-run (no flag). Chosen.
- B. Explicit `weave-slices --expand` flag. Rejected.
- C. Separate `weave-promote` skill. Rejected.

### `weave-prepare` disposition

- A. No CLI extension; skill stays. Considered.
- B. Drop skill entirely; prep folds into `weave-execute`. Chosen.
- C. Drop CLI + skill; `weave-execute` does git directly. Rejected (the existing CLI works fine).

### `weave-issues` disposition

- A. Ship `weave-slices` alongside; deprecate later. Rejected (ceremony with no users).
- B. Hard rename `weave-issues` -> `weave-slices`. Chosen.
- C. Shim - `weave-issues` becomes a thin pointer. Rejected (skills aren't callable functions).
- D. Evolve `weave-issues` in-place with same name. Rejected - terminology drift, name mismatch with new model.

### Critical-path bias for `weave-next`

- A. Prefer slices on the critical path. Chosen.
- B. Lowest slice ID. Rejected.
- C. List all, let engineer choose. Rejected - too much friction.

### Cross-slice task dep syntax

- A. Disallow in v1. Chosen.
- B. `01/T3` (slash). Available if needed later.
- C. `01:T3` (colon). Rejected (visual collision risk).
- D. `01.T3` (dot). Rejected (looks like property access).

### Backwards compatibility

- A. Dual mode in skills, no forced deprecation. Chosen.
- B. Migration tool `weave migrate-to-slices`. Rejected.
- C. Hard cutover. Rejected.

## Rejected Approaches

- Companion `task-slices/index.yml` machine-readable rollup. Markdown rollup is sufficient.
- `task-slices/index.md` with mermaid diagram. ASCII tree alone suffices.
- Persisting `waves` in any artifact. Computed implicitly in the "Parallel work" markdown section.
- `weave-findings` dedicated skill. `weave-fix` + `weave-clarify findings` cover the surface.
- `bug.md` change-root artifact for fix-type. `findings.md` chosen instead (user preference).
- Broadening `exploration.md` to be "change intent" for all types. Lane-specific artifacts respected.
- `weave-fix` producing a flat `tasks.md` for trivial fixes. Always slice folder.
- `--expand` / `--promote` flags on `weave-slices`. Idempotent re-run sufficient.
- New CLI flags `--slice <NN>` on `weave task prepare`. Branches are change-level; no slice-awareness needed.
- `--repo <name>` filter on prepare. Slice-level prepare is enough.
- Migration tool for legacy flat `tasks.md`. Dual-mode skills handle the transition naturally.
- Deprecation banner + parallel skills for `weave-issues` -> `weave-slices`. Hard rename simpler with no users.
- Cross-slice task deps in v1. Slice-level deps via `depends_on` only.

## User Preferences

- Markdown-and-CLI everywhere. Avoid YAML where markdown can carry the same info.
- No CLI proliferation. Reuse what exists; add new commands only when behavior is novel.
- No skill proliferation. Fold new behavior into existing skills when sensible.
- Consistency over ceremony for trivial cases. `findings.md` required even for typo fixes so all fix-type changes look the same.
- Single mental model preferred to lots of conditional behavior. Slice folder is the unit for all changes (no flat exception for fix-type).
- Tolerate residual git conflicts. Markdown + git's limits accepted.
- Hard cutovers acceptable given no users. No deprecation ceremony for ceremony's sake.
- Plan mode for design, agent mode for execution. Clean separation.
