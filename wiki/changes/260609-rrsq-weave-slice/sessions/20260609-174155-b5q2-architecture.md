# Session Capture: Architecture - 2026-06-09 (Rollup Library Pivot)

## Summary

Third architectural session for the task-slices model. Re-opened the rollup/hook design after the user's hard constraint: "do not selectively support like claude, cursor like that - it should be agnostic of harness, or be it any harness it should be able to use it." Compared harness-specific PostToolUse registration (editor-local settings, defensive parse, git auto-stage on derived files) against Weave's constraints. Under the harness-agnostic requirement, PostToolUse hooks are ruled out entirely, and since Weave skills ARE the primary writers in the agent-driven happy path, the "hook" abstraction collapses into "every writer calls a shared library inline." Locked in writer-derives with `weave slice rollup` CLI for non-skill writers. Batched trigger granularity (once per `weave-execute` episode). Unconditional regeneration of `dependency-graph.md`. Pre-commit installer deferred to a future release. Architecture and implementation plan revised to match.

## Decisions Made

### Trigger mechanism: writer-derives, no editor hooks

- Drop the PostToolUse hook framing entirely. No `.claude/settings.local.json` registration, no Cursor harness config, no Codex / Opencode equivalents.
- Single shared library at `src/lib/sliceRollup.ts` is the sole source of truth for derived slice state.
- Every Weave skill that writes primary state calls the library inline after the write.
- A `weave slice rollup` CLI wraps the same library for non-skill writers (manual editor edits, post-merge resolution, CI checks).

### Trigger granularity: batched per episode

- Library runs once per logical write episode, not after every individual `tasks.md` write.
- Episode boundaries in `weave-execute`:
    1. End of episode (all selected tasks completed).
    2. Before any HITL pause (so human sees fresh state).
    3. Before any error exit.
    4. After `weave-slices` / `weave-fix` finishes scaffolding new slices.
    5. Manual `weave slice rollup` CLI invocation (humans, pre-commit hooks, CI).
- Intermediate views of `status.yml.task_summary` during a long agent run may be stale; they reconverge at the next boundary. Acceptable cost.

### `dependency-graph.md` regeneration: always

- Unconditional regen on every batched rollup. The file is a pure deterministic function of `{id, title, status, depends_on, owner}` across all slices; cost is negligible (small yaml parses + one markdown write).
- Conditional regen with diff detection rejected — saves ~milliseconds; adds complexity and risk of skipping a needed update.

### Structure of `dependency-graph.md`: confirmed

Sections kept as previously sketched: Purpose, Graph (ASCII tree with multi-parent duplication), Slice dependencies table (`| Slice | Depends on | Status | Owner |`), Ready to work now, Blocked slices, Critical path (longest dep chain by node count; tiebreak on slice numeric prefix), Parallel work (narrative naming the largest parallel group off the critical path).

### Engineering patterns adopted

Even though Weave drops the harness-coupled hook framing, two patterns are explicitly adopted in `sliceRollup.ts`:

- **Defensive parser:** only update derived counters when their section headers parse cleanly in the new content; leave previous values otherwise. Prevents partial-write corruption.
- **Auto-stage derived files:** every rollup `git add`s the derived files (`status.yml`, `dependency-graph.md`) so they never block a subsequent commit.

### CLI surface

```text
weave slice rollup [--slice <path>] [--all] [--check]
```

- `--slice <path>`: rollup a single slice.
- `--all` (default): rollup every slice in the active change + regenerate `dependency-graph.md`.
- `--check`: dry-run mode; exits non-zero if derived files would change.

### Pre-commit hook installer: skip for v1

- Not shipped in v1. `weave slice rollup --check` exists; teams that want auto-derivation on every commit wire it into pre-commit / husky / lint-staged / CI on their own.
- Revisit if non-skill writes (manual editor edits, post-merge) prove to be a real drift source in practice.

### Cycle detection: write succeeds, banner in graph

- Cycle in `depends_on` doesn't fail the primary write. The library detects, writes everything else successfully, and adds a `WARNING: dependency cycle detected, graph not regenerated` banner to `dependency-graph.md` until the cycle is resolved.

## Options Considered

### Editor PostToolUse hook coverage

- A. Claude Code only (harness-specific PostToolUse registration). Rejected - violates harness-agnostic constraint.
- B. Claude Code + Cursor (architecture's prior scope). Rejected - same reason.
- C. Claude Code + Cursor + Codex + Opencode. Rejected - N harness configs to ship and test for marginal benefit.
- D. CLI-only, users wire harness hooks themselves. Considered as a baseline, then improved upon.
- E. Writer-derives + CLI fallback. Chosen.

### Trigger granularity

- A. After every single `tasks.md` write (per-task). Considered. Cost is tiny; always-fresh state.
- B. Batched per `weave-execute` episode. Chosen. Amortizes I/O, keeps the agent loop tighter, intermediate staleness is harmless because the next boundary reconverges.
- C. Hybrid (per-write for status.yml, batched for dependency-graph.md). Rejected - more complex with no real benefit since the library already does both in one call.

### Episode boundaries

- A. End-of-episode only. Rejected - misses HITL pauses (human sees stale state) and error exits (state may be inconsistent on recovery).
- B. End + HITL + error + scaffolding + manual CLI (5 boundaries). Chosen. Comprehensive.
- C. End + manual CLI only (2 boundaries). Rejected - too sparse.

### `dependency-graph.md` regen policy

- A. Always regen on every batched rollup. Chosen. Simpler code; cost negligible.
- B. Conditional regen only when `{status, depends_on, owner, title}` changed for any slice. Rejected - marginal perf win for noticeable code complexity.

### Pre-commit installer

- A. Ship `weave init --git-hooks` and default it on. Rejected for v1 - adds install-time complexity before we know if drift is a real problem.
- B. Ship as explicit opt-in (default off). Rejected for v1 - same reason.
- C. Skip for v1; `--check` exists for users who want to wire pre-commit themselves. Chosen.

## Rejected Approaches

- PostToolUse hooks per agent harness (any combination - Claude only, Claude+Cursor, all four).
- Filesystem watcher daemon (`weave watch`). Rejected - adds a process to manage for a marginal real-time-freshness gain.
- Per-write rollup. Rejected in favor of batched.
- Conditional `dependency-graph.md` regen with diff detection. Rejected - complexity not worth ms savings.
- Pre-commit hook installer in v1. Deferred until drift proves to be a real problem.
- Mandatory CI check for drift. Out of scope; `--check` exists for opt-in adoption.

## User Preferences

- Harness-agnostic: any agent, any editor, any IDE, any workflow must work the same.
- Minimum infrastructure: don't ship multi-harness configs if one library + one CLI does the job.
- Simpler code over micro-optimizations: unconditional regen, batched triggers, no diff detection.
- Defer install-time complexity (pre-commit installer) until drift proves real.

## Agent Recommendations

- Implement the library first as standalone deliverable (T4 / `rollup-library` todo); wire writers to call it as part of their respective todos (T2 weave-fix, T3 weave-slices, T5 slice-aware weave-execute).
- Adopt defensive parser + auto-stage patterns in `sliceRollup.ts` - they solve the partial-write and git-blocking problems we'd face.
- Capture the writer-derives rationale in the knowledge doc (`wiki/knowledge/domains/change-workflow/features/task-slices/behavior.md`) so future Weave contributors understand why we don't ship harness hooks.

## Unresolved Points

- **Defensive parser exact heuristics.** Determined empirically during implementation. Specifically: how to distinguish an intentionally-empty section from an in-progress write that hasn't yet written that section. Likely answer: trust the section header presence; if heading exists, parse contents; if heading absent, leave previous derived value alone.
- **Pre-commit installer in a future release.** Worth revisiting if manual editor edits or post-merge resolution prove to be a frequent drift source.
- **Cross-cutting heading literal name** (carried over from prior session). `## cross-cutting` is the working choice; confirm on first real slice generation.
- **Flat-mode dispatch removal timeline** (carried over). No forced timeline.
