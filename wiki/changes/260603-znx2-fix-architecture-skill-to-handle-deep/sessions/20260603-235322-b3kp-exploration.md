# Session Capture: Exploration - 2026-06-03

## Summary

Brainstorm + interview session about extending the `weave-architect` skill so the `architecture` artifact can scale from a single file (today's only shape) to a multi-file folder for larger, multi-system changes — without forcing one shape on every change. The conversation grew to cover three coupled improvements: (1) make the artifact's on-disk shape file-or-folder per change with agent-decided default and user-pin override, (2) extract the artifact's content shape (sections, filenames) from the skill's prose into a team-customizable repo template, and (3) tighten the skill responsibility split so `weave-architect` is purely Plan-Mode (design + propose only) and `weave-capture` / `weave-clarify` are the folder-aware Agent-Mode executors. A plan was drafted at `.cursor/plans/architecture-folder-mode_*.plan.md` and is the implementation scaffold.

## Decisions Made

1. The `architecture` artifact has two valid on-disk shapes: single file `architecture.md` (today) or folder `architecture/` (new). Lane identity and status.yml semantics are unchanged; only the on-disk shape varies.
2. The agent decides shape per change based on enumerated signals (subsystems touched, schema+API+UI combined, phased rollout, projected size). It always explains its decision. User can pin via natural language at invocation ("use folder mode" / "single file is fine"). No repo-level preference setting.
3. The architecture template lives as scaffold .md files, not a YAML manifest. Each scaffold may carry optional frontmatter `purpose:`, `required:`, `order:`.
4. Bundled defaults live at `templates/architecture/`; per-repo overrides live at `.weave/architecture-template/`. `weave init` copies bundled into repo. The skill lazy-falls-back to bundled if the repo override is absent.
5. Single-file is also template-driven. There is no special-case template inside the skill — both single-file (`templates/architecture/single-file.md`) and folder (`templates/architecture/folder/...`) are external scaffolds.
6. `weave-architect` becomes Plan-Mode-only. The existing `# Output Path`, `# Lifecycle Progress`, `# Lifecycle Staleness Verification`, and the embedded 17-section template all move out of its prose.
7. `weave-capture` and `weave-clarify` both become folder-aware and template-driven. Both can write one file or many. Split is by intent (persist new material vs refine existing), never by file count.
8. Lifecycle progress (`weave change progress architecture`) is called by capture and clarify, never by architect.
9. Existing 11 single-file `architecture.md` files are left untouched. File mode is permanently supported.
10. Template-drift tracking is out of scope for this change. It is punted to a follow-up Weave change that can borrow the existing `last_changed_in` / `weave agent update` machinery.
11. Extending the same customizable-template pattern to PRD and exploration is out of scope. Library code should be parameterized over artifact name so future extension is cheap.

## Options Considered

- **Template shape**: scaffold .md files (chosen) vs YAML manifest vs free-form markdown convention doc vs scaffold+manifest hybrid. Picked scaffold .md files for user-friendliness, dev-friendliness, and symmetry with how Weave already ships `templates/skills/`.
- **Trigger model**: pure agent judgment vs agent-default-with-user-hint (chosen) vs repo-level preference vs explicit-only.
- **Skill responsibility split for new operations**: clarify-handles-single-file / capture-handles-multi-file vs capture-handles-rewrites / clarify-handles-tweaks vs relax architect to write vs no-segregation-both-can-write-any-count (chosen).
- **Existing changes**: leave alone (chosen) vs soft notice when team template drifts from old content vs active migration command.
- **Template drift handling**: borrow skill-update machinery (`last_changed_in`) vs no drift tracking vs CHANGELOG only vs punt to follow-up (chosen).

## Rejected Approaches

- YAML manifest as the template format: too dev-flavored; teams would naturally want full markdown sections with headings, guidance, and examples — which is what scaffold .md files already provide.
- Free-form markdown convention doc as the template: non-deterministic; two engineers reading the same doc would produce different folders.
- Repo-level `architecture.default_shape` preference: adds config surface without enough payoff over natural-language pinning.
- Asking the user "single file or folder?" every time: adds friction; the agent can decide and explain transparently.
- Architect-in-Agent-Mode writes for deepen / convert: cleanly breaks the Plan-Mode-only invariant.
- File-count-based segregation between capture and clarify (e.g. "clarify = exactly one file, capture = many"): fragile; user-intent is the cleaner pivot.
- Auto-migrating existing single-file architectures: surprise behavior; opt-in conversion is safer and lower-risk.
- Shipping template drift tracking in this change: scope creep; the customizable-template story already pulls in 6 skills, library, knowledge, and tests.

## User Preferences

- Decouple the architect skill from the artifact's content shape: the skill should *reference* the template, not embed it. Teams can iterate on the template without touching the skill, and we can iterate on the skill without invalidating any team's template.
- Symmetric customizability: even the single-file architecture should be team-editable, not only the folder shape.
- Architect stays in Plan Mode through and through. File writes belong to `weave-capture` / `weave-clarify`, not architect.
- No rigid file-count split between capture and clarify. Both should be able to execute the architect's plan regardless of whether it touches one file or many.
- Brainstorm first, then interview. The user explicitly asked for an exploratory framing before any structured Q&A. Interview was paced one question at a time through `AskQuestion`.

## Agent Recommendations

- Bundled `templates/architecture/folder/` should mirror the existing 17-section architect template, picking ~12 sections as standalone files: `index.md` (frontmatter + summary + ToC), `proposed-architecture.md`, `data-model.md`, `api-contracts.md`, `data-flow.md`, `decisions.md`, `rollout-and-migration.md`, `observability.md`, `testing.md`, `security.md`, `risks.md`, `open-questions.md`.
- Bundled `templates/architecture/single-file.md` carries the existing 17-section content verbatim — drop-in compatible with today's behavior.
- Per-file scaffold frontmatter is optional but uses three keys: `purpose:` (one-line description, surfaced in deepen prompts), `required: bool` (drives substantive-content check), `order: int` (deterministic index ToC ordering).
- `weave init` copies bundled templates into `.weave/architecture-template/`; the skill lazy-falls-back to bundled if the repo override is absent. Existing repos do not need to re-init.
- `hasSubstantiveMarkdown` becomes template-aware: substantive when all `required: true` scaffold files have content beyond their guidance comments.
- `tasks.md` `source:` field should be normalized to the lane name `architecture`, not `architecture.md`. Existing inconsistent files left alone (some already use `architecture`, some `architecture.md`).
- Capture should write the folder atomically (temp + rename) to avoid half-written state on failure.
- CLI library code should be parameterized over artifact name so the same pattern extends cheaply to PRD/exploration later.
- Tightening architect to never write is a real behavioral change. Old conversations ending in "save it" still succeed because capture/clarify take over.

## Unresolved Points

- Exact folder layout under `.weave/architecture-template/` — `single-file.md` at root + `folder/<sections>.md` (current bias), or two symmetric subfolders `single-file/architecture.md` + `folder/index.md...`. Minor; pick during phase 1.
- Whether "add a new section file to an existing folder" routes through capture (structural) or clarify (single-file write). Bias toward capture; either is acceptable.
- Exact contents and ordering of the bundled `folder/` scaffold — proposed list above but final phrasing and starter content to be settled during phase 1 implementation.
- Whether `weave-clarify` accepts multi-file cross-cutting amendments in v1 or defers to follow-up. Bias toward v1.
- Atomic write strategy for folder mode (temp dir + rename, vs. per-file write with rollback). Implementation detail.
