# Session Capture: Exploration - 2026-05-31

## Summary

Discussed how Weave should handle multiple session-only captures when the corresponding live artifact is missing or already exists.

The agreed direction is to introduce pending session context: session-only notes remain non-canonical resume context, but bare `weave-capture` should consider relevant pending notes when creating or updating the selected live artifact.

## Decisions Made

- Treat session-only notes as pending context until the live artifact is updated.
- If the target artifact is missing, bare `weave-capture` should consider all session notes for that lane.
- If the target artifact exists, bare `weave-capture` should consider only lane session notes created after the artifact frontmatter `updated_at`.
- Use artifact frontmatter `updated_at` as the cutoff, not filesystem mtime.
- Do not add per-session promotion status in v1.
- Once the artifact is updated, older considered session notes naturally fall before the cutoff and should not be reconsidered.
- Downstream tools should trust live artifacts and should not quietly synthesize from pending session-only notes.
- `weave-next` should surface pending session context and recommend bare `weave-capture` before downstream progress.

## Options Considered

- Per-session promotion metadata: rejected for v1 because the timestamp cutoff solves repeat processing without extra state.
- Always reading all old sessions: rejected because it would repeatedly process historical context and could revive obsolete details.
- Current discussion only: rejected because it loses durable discoveries captured in earlier session-only notes.
- Artifact `updated_at` cutoff: selected because it keeps the model simple and aligned with canonical artifact updates.

## Rejected Approaches

- Do not use filesystem mtime as the artifact freshness source.
- Do not make downstream skills silently depend on unpromoted session notes.
- Do not add a dedicated promotion database or per-session status in v1.

## User Preferences

- The user wants older session-only details to be preserved and considered when creating an artifact.
- The user wants existing artifacts updated only from sessions newer than the artifact update cutoff.
- The user prefers the simple timestamp cutoff over explicit promotion status.
- The user wants the workflow thought through for both missing-artifact and existing-artifact cases.

## Agent Recommendations

- Update `weave-capture` skill instructions to define pending session context promotion.
- Update `weave-next` to detect and report pending session context.
- Update downstream lane skills to avoid proceeding from artifacts that have newer unpromoted session context.
- Keep v1 skill-driven; no compiled capture command is required unless deterministic timestamp comparison becomes necessary later.

## Unresolved Points

- Exact handling for legacy session filenames without full timestamps.
- Whether downstream skills should hard-stop or warn when pending upstream session context exists.
- Exact wording for `weave-next` pending-context recommendations.
