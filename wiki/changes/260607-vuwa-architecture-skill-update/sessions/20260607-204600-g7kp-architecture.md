# Session Capture: Architecture - 2026-06-07

## Summary

The discussion focused on making `weave-architect` account for team-specific design guidance during architecture conversations. The user wants a user-editable file where teams can record local design considerations, common pitfalls, preferred patterns, and things architecture agents should keep in mind before recommending how something should be built.

## Decisions Made

- Add a team-owned architecture considerations file under `.weave/architecture-considerations.md`.
- Scaffold the file during `weave init`.
- Treat the file as user-owned: Weave may create it once, but should not overwrite or edit it after creation.
- Update `weave-architect` so architecture discussions read this file when present and use it as advisory team guidance.
- Use the corrected spelling `architecture-considerations.md`.
- Scaffold a lightweight starter template rather than a blank file, so teams have a useful shape without inheriting a mandatory philosophy.

## Options Considered

- Store guidance under `wiki/knowledge/shared/architecture-guardrails/behavior.md`.
- Use a repo-root file such as `ARCHITECTURE-GUARDRAILS.md` or `DESIGN-CONSIDERATIONS.md`.
- Store it under `.weave/architecture-considerations.md`.
- Use a hybrid approach that prefers `wiki/knowledge/**` and reads conventional repo-root files.

## Rejected Approaches

- Do not bake universal architecture advice directly into `weave-architect` as mandatory discussion points.
- Do not make the file blank; it should include a small user-owned template.
- Do not force the skill to discuss every possible concern, such as N+1 queries, caching, events, observability, or service object usage, on every architecture response.
- Do not let Weave rewrite the file after the user customizes it.

## User Preferences

- Teams should own their architecture guardrails because every team may have different preferences.
- The guidance should be external to the skill and editable by users.
- The architecture skill should keep the guidance in mind during design discussion and recommendations.
- The skill should avoid common pitfalls according to the team's own file, not according to a hardcoded global checklist.

## Agent Recommendations

- Use `writeFileIfMissing` in the scaffold path so `.weave/architecture-considerations.md` is created only when missing.
- Add the scaffold through `src/lib/weave-scaffold.ts`, since that path already owns `.weave/` setup.
- Add `weave-architect` instructions to read `.weave/architecture-considerations.md` when present, never edit it, apply relevant guidance silently, and surface only constraints, conflicts, or risks that materially affect the current design.
- Keep the starter template concise, with sections for design principles, preferred patterns, patterns to avoid, data access and scaling, caching and consistency, async boundaries and events, observability and operations, and notes for agents.
- Add tests for scaffold creation, non-overwrite behavior, and skill contract text.

## Unresolved Points

- Exact starter-template wording can be refined during implementation.
- Whether the installed `.claude` and `.agents` skill copies should be updated manually in the same change depends on this repo's existing template-alignment test expectations.
