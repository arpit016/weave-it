# Session Capture: PRD - 2026-06-05

## Summary

The discussion identified a follow-up change after making `weave add` and `weave workspace` workspace-aware. The remaining problem is that `weave change ...` and `weave artifact ...` commands still resolve their target from `realpath(cwd)` and `session.folders`, so running them from inside a workspace sub-repo misses the workspace-level `wiki/changes/`.

The product direction is to simplify the model instead of extending multi-target behavior:

- Workspace mode should use a workspace-only change store: `workspace/wiki/changes/` is the single durable place for changes and artifacts.
- Sub-repos registered in `workspace.yml.repos` should not get their own `wiki/changes/` by default.
- `--target` behavior is no longer needed for change and artifact commands.
- `weave change propagate` is no longer needed and should be removed completely.

## Decisions Made

- Use a workspace-only model for change and artifact state in workspace mode.
- Remove `--target` from `weave change` and `weave artifact` commands rather than trying to reinterpret it as sub-repo scope.
- Remove `weave change propagate` completely because one workspace-level change store makes intra-workspace propagation unnecessary.
- In workspace mode, `cd peoplebox-platform/billing && weave change current` should walk up to the workspace root and report the workspace's active change.
- In repo mode, commands should also walk up to the repo's Weave root instead of treating an arbitrary subdirectory as its own change root.
- Keep `status.yml` schema unchanged for this change; do not add `scope` or `targets`.

## Options Considered

- Keep `--target` and make it resolve `workspace.yml.repos` ids. Rejected because it keeps the user-facing multi-target model alive after the product chose workspace-only change state.
- Treat `--target <sub-repo>` as a scope tag inside the workspace-level change. Rejected for now because removing `--target` is simpler and avoids introducing a new `status.yml.scope` field.
- Keep `weave change propagate` for repo-mode only. Rejected because the command's core product meaning is multi-folder copying, which is no longer part of the desired v1 change model.
- Per-sub-repo `wiki/changes/`. Rejected because the current workspace model deliberately keeps sub-repos as implementation locations, not independent Weave artifact stores.
- Hybrid workspace specs plus sub-repo tasks. Rejected as too complex for this follow-up.

## Rejected Approaches

- Do not eagerly make all skills deeply workspace-aware in this change. The first product behavior to fix is CLI command resolution and removal of obsolete surfaces.
- Do not create sub-repo branches or sub-repo Weave scaffolds from `weave change new`.
- Do not add a new clone/missing-repos workflow here; that remains separate workspace lifecycle work.

## User Preferences

- Favor simplifying the user model over preserving legacy multi-target behavior.
- Prefer deleting obsolete behavior (`--target`, `weave change propagate`) instead of layering compatibility around it.
- Keep workspace mode coherent: a workspace has one Weave change/artifact store, and sub-repos are registered folders inside that workspace.

## Agent Recommendations

- Implement this as a focused follow-up change before updating all skills broadly.
- Centralize target resolution behind a `findWorkspaceMode(cwd)`-driven helper used by all change and artifact commands.
- Remove the propagate skill and docs at the same time as the CLI command so agents do not keep recommending a deleted workflow.
- Update `weave-new` and `weave-next` minimally because they directly reference `--target`, `change current all`, or propagation-style multi-target assumptions.

## Unresolved Points

- Whether public JSON response shapes should keep existing plural `targets: [...]` with a single element for compatibility, or collapse to singular `target`. Recommendation: keep plural for now to reduce consumer churn.
- Whether removed CLI options should produce custom migration errors or rely on Commander unknown-option errors. Recommendation: Commander errors are acceptable for v1.
- Whether existing users with sub-repo-local `wiki/changes/` need migration or warnings. Recommendation: out of scope for this PRD.
