# Session Capture: Architecture - 2026-06-05

## Summary

The architecture discussion settled the implementation shape for making `weave change` and `weave artifact` commands workspace-aware. The key technical direction is to route every affected command through a single cwd-dispatched context resolver that walks up from `cwd` using the existing workspace mode helper, then operates on exactly one change root.

The design keeps the public JSON `targets: [...]` shape as a one-element array for compatibility with skills, tests, and existing consumers. It removes the CLI-level multi-target surface (`--target`, `all`, and `weave change propagate`) instead of keeping compatibility shims.

## Decisions Made

- Use `findWorkspaceMode(cwd)` as the canonical mode detector for all change and artifact commands.
- In workspace mode, resolve all change and artifact state to the workspace root, even when commands run from a registered sub-repo.
- In repo mode, resolve nested directories to the repo root.
- Preserve the current `targets: [...]` JSON shape as a one-element array.
- Outside any Weave context, throw `ChangeCommandError("no_weave_context", ...)` so JSON callers receive the existing `{ status: "error", code, message }` pattern.
- Remove `--target` from change and artifact commands.
- Remove `weave change propagate` and the `weave-propagate` skill entirely.

## Options Considered

- Collapse JSON output to a singular `target` object.
- Keep `--target` as a no-op or compatibility alias.
- Auto-register workspace sub-repos into `session.folders` during change/artifact resolution.
- Keep `weave change propagate` for repo mode only.

## Rejected Approaches

- Singular JSON was rejected because it would force avoidable churn across tests, skills, and downstream JSON consumers.
- `--target` compatibility shims were rejected because they preserve a misleading multi-target mental model.
- Auto-registering sub-repos was rejected because it would mutate session state and contradict the workspace-only change store model.
- Keeping `propagate` for repo mode was rejected because the command's primary purpose conflicts with the chosen workspace-only model.

## User Preferences

- Prefer a simplified command model over preserving obsolete compatibility behavior.
- Prefer workspace-level change artifacts only; sub-repos should not get their own `wiki/changes/` by default.
- Prefer deleting obsolete command and skill surfaces rather than keeping compatibility aliases.

## Agent Recommendations

- Add a shared `resolveChangeContext(cwd, sessionPath?)` helper near the workspace mode helpers.
- Rewire all public change and artifact library functions to resolve one context from `cwd`.
- Keep result envelopes stable with one-element `targets` arrays.
- Add tests for workspace-mode cwd walk-up, repo-mode cwd walk-up, and no-context failure.
- Update skill templates, installed skills, README, and knowledge docs in the same change to avoid stale agent guidance.

## Unresolved Points

None blocking. Future cleanups could revisit whether JSON should eventually collapse from `targets` to `target`, but this change preserves compatibility.
