# Session Capture: Exploration - 2026-06-04

## Summary

Resolved the product shape of "add a repo/folder to a workspace" as a mode-aware extension of `weave add` rather than a new command. In workspace mode, `weave add` becomes the canonical command for growing a workspace by registering an existing folder, adopting an external folder, or cloning from a git URL. In repo mode, behavior is unchanged. Internally, the "register repo into workspace" step from `weave init --mode workspace` is extracted into a shared helper.

## Decisions Made

- Extend the existing `weave add` command rather than introducing a new command. Mode is detected at runtime via the active workspace's `.weave/workspace.yml` `mode` field.
- In repo mode, `weave add` is unchanged: writes only to `session.folders` in `~/.cache/weave/current-session.yml`. No `workspace.yml` or `.gitignore` writes. Accepts only `<path>`.
- In workspace mode, `weave add` accepts either `<path>` or `<git-url>`:
  - URL form clones into workspace root using the URL's repo basename (`git@github.com:foo/bar.git` -> `./bar`). No override flag.
  - Path inside the workspace registers the folder in place.
  - Path outside the workspace adopts the folder: moves it into the workspace root, mirroring `initWorkspaceFromGitRepo`.
- In all workspace-mode cases, after the folder is in place:
  - Add `/<dirname>/` to the workspace `.gitignore` (idempotent).
  - Write `.weave/workspace.yml` entry `repos.<slug> = { path, kind, remote? }`.
  - Capture `remote.origin.url` via `getGitRemote` when the folder has a `.git/`. Omit the `remote` field when absent.
- Workspace-mode `weave add` does NOT write to `session.folders`. This matches `weave init --mode workspace`'s existing behavior, where only the workspace itself is in session state and sub-repos live exclusively in `workspace.yml.repos`. Lazy growth via `ensureFolderInSession` continues to cover the rare case where a sub-repo is itself `weave init`'d and acquires its own `wiki/`.
- Non-git folders in workspace mode are still registered in `workspace.yml.repos` and added to `.gitignore`. The `remote` field is simply omitted. `repos` keeps its name despite being slightly fuzzy for non-git entries.
- An already-registered path is an idempotent no-op with a clear message, matching today's `addFolderToSession` "already_exists" behavior.
- Internal refactor: factor the "register repo into workspace" step out of `scaffoldWorkspace` in `src/lib/init-workspace.ts` into a shared helper consumed by both init and add. Keeps parity automatic.

## Options Considered

- Mode-aware `weave add` (chosen) vs. new `weave workspace add` subcommand. Chose extension because the user-facing verb is the same and the dual-command surface adds discoverability cost.
- Pure refactor of session vs. workspace registries (Option B from discussion) vs. keep dual registries (chosen). Chose to keep the dual registries because the change is genuinely additive and v0.x posture leaves room to refactor later if it gets painful.
- Updating `session.folders` for newly-added sub-repos vs. not updating it (chosen: do not update). Chose non-update for parity with init's existing workspace-mode behavior and because sub-repos do not have their own `wiki/` in the default case, so per-folder state has nothing to track.

## Rejected Approaches

- Allowing `weave add` to refuse outside-workspace paths and forcing users to `mv` manually. Rejected because the user explicitly wants `weave add` to adopt outside paths the same way init does.
- Supporting a `--into <dirname>` override or a second positional arg for URL clone destination. Rejected to keep the URL path minimal; users who need a non-default name can clone manually then `weave add ./renamed-dir`.
- Deprecating `weave add` in repo mode entirely. Rejected because the multi-folder repo-mode pattern is still useful for power users who want lightweight cross-repo browsing without committing to workspace mode.
- Renaming `workspace.yml.repos` to `folders` or `entries`. Rejected to avoid a migration burden for early adopters.

## User Preferences

- Strong preference for minimum disruption to existing behavior and existing data files. No registry restructuring in this change.
- Strong preference for the canonical workflow being: workspace mode for multiple repos, repo mode for single repos.
- Strong preference for `weave add` doing the right thing automatically based on mode, rather than splitting into multiple commands.

## Agent Recommendations

- When implementing, extract a `registerRepoIntoWorkspace({ workspacePath, sourcePath, id?, kind? })` helper that handles the gitignore append + workspace.yml write + optional adopt/move. Call it from both `initWorkspaceFromGitRepo` and the new workspace-mode branch of `addFolder`.
- Detect URLs by scheme prefix (`git@`, `https://`, `http://`, `ssh://`, `git://`) before resolving as a filesystem path.
- Use the existing `getGitRemote(folderPath)` helper for capturing the remote URL; it already handles the "no git" case by returning undefined.
- Treat `.gitignore` append as idempotent: read the file, skip if the entry already appears (literal match on `/<dirname>/`).
- Update knowledge doc `wiki/knowledge/domains/cli-commands/features/core-command-reference/behavior.md` to document the mode-aware `weave add` semantics, and update the README's `weave add` section in parallel.
