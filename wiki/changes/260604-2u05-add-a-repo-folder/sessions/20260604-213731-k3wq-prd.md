# Session Capture: PRD - 2026-06-04

## Summary

Refined the PRD after the user pushed back on an overreach in my earlier framing. Confirmed that the workspace-mode `weave add` writes only to `workspace.yml.repos` (not to `session.folders`), and bundled the `weave workspace` mode-aware observability fix into this change so users can actually see the result of their adds.

## Decisions Made

- `weave add` is mode-aware. Mode is determined by walking up from `cwd` to find `.weave/workspace.yml`. If found with `mode: workspace`, treat as workspace mode. Otherwise treat as repo mode. This rule does not depend on session state, so it survives session resets and fresh clones.
- Workspace-mode `weave add` writes only to `workspace.yml.repos` and `.gitignore`. It does not write to `session.folders` for the added repo. The workspace itself remains the only session entry.
- `weave workspace` becomes mode-aware in the same change. Per session folder:
  - If the folder is workspace mode (per the workspace.yml lookup rule above), `weave workspace` reads its `.weave/workspace.yml.repos` and includes those entries in both text and JSON output.
  - If the folder is repo mode (or workspace.yml is missing/unparseable), `weave workspace` falls back to today's behavior: show only the session folder itself.
- Graceful degradation in `weave workspace`: if `workspace.yml` is missing or unparseable for a folder marked `kind: workspace` in session, show only the folder itself without a warning and without crashing. Treat as if the folder had `mode: repo` for display purposes.
- Accept as known v1 limitations:
  - `weave change <subcommand> --target all` will not fan out to sub-repos in workspace mode (it enumerates `session.folders`, which holds only the workspace).
  - `weave change <subcommand> --target <short-id>` will not resolve sub-repos in workspace mode unless lazy-grown via a prior per-folder command.
  Both are acceptable because sub-repos in default workspace mode do not have their own `wiki/changes/`. Lazy growth still covers the rare case where a sub-repo is itself `weave init`'d.
- The JSON output of `weave workspace` gets an additive `repos` field per workspace folder. Existing consumers that ignore unknown fields continue to work.
- The text output of `weave workspace` indents the repos list under each workspace folder.
- Init's existing behavior is already aligned: it writes only to `workspace.yml.repos` for adopted repos. The new `weave workspace` enhancement will, as a side benefit, finally surface the adopted repo in `weave workspace` output (which it doesn't today).

## Options Considered

- Reading B (write to both registries in workspace mode) vs Reading A (write only to workspace.yml.repos). Chose Reading A because Reading B only solves the observability problem for the local user; teammates and fresh clones would still see stale `weave workspace` output. Reading A combined with the `weave workspace` enhancement covers all observers.
- Belt-and-suspenders (write to both AND read workspace.yml in show-workspace). Rejected as unnecessary churn once `show-workspace.ts` reads `workspace.yml.repos` as the committed truth.
- Defer the `weave workspace` enhancement to a follow-up change. Rejected because shipping `weave add` without `weave workspace` observability creates a visible UX gap users will immediately notice.

## Rejected Approaches

- Mode detection by reading `session.folders[<folder>].kind` alone. Rejected because it couples mode detection to ephemeral session state and would break after a session reset or for teammates with a fresh session.
- Surfacing a warning when `workspace.yml` is missing for a folder marked workspace in session. Rejected as noisy; degrading silently to "show only the folder" is the kinder UX.
- Filling `--target all` and short-ID gaps by deriving sub-repo targets from `workspace.yml.repos`. Out of scope for v1; left as a documented limitation.

## User Preferences

- Strong preference for symmetric mode awareness: both `weave add` and `weave workspace` should make the same mode decision the same way.
- Strong preference for keeping the dual-registry split clean: `session.folders` is local ephemeral state, `workspace.yml.repos` is committed truth, and they don't overlap for sub-repos.
- Strong preference for shipping the `weave workspace` enhancement together so the feature is observable end-to-end.

## Agent Recommendations

- Implement a single mode-detection helper (suggested name: `findWorkspaceMode(cwd) -> { mode, workspacePath } | undefined`) that walks up from `cwd` to find `.weave/workspace.yml` and parses its `mode` field. Reuse this from `weave add`, `weave workspace`, and any future workspace-aware command.
- In `show-workspace.ts`, branch per session folder. For workspace folders, read `<folder>/.weave/workspace.yml` and parse `repos`. On parse failure or missing file, return repos as undefined and fall back to repo-mode display for that folder.
- Update the knowledge doc `wiki/knowledge/domains/cli-commands/features/core-command-reference/behavior.md` to:
  - Add a `Command: weave add` section documenting the mode split.
  - Remove the "does not inspect `.weave/workspace.yml`" and "does not list repos from workspace metadata" lines from the `weave workspace` section.
  - Add documentation of the new workspace-mode `weave workspace` output, including JSON shape.
- Update the README's `weave add` and `weave workspace` sections in parallel.
