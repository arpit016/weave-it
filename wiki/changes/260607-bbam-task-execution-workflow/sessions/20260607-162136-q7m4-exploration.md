# Session Capture: Exploration - 2026-06-07

## Summary

Explored the product behavior for a new `/weave-execute` workflow after the task prepare workflow. The desired v1 is agent-first and local-only: the user invokes `/weave-execute`, the agent selects or confirms the task set, prepares the selected task repos through the existing prepare workflow, implements tasks, verifies them, and updates local `tasks.md` status and evidence.

The discussion deliberately separated v1 from a deterministic `weave task execute` CLI. The CLI is not part of v1 because deterministic command code cannot safely implement arbitrary task code without a first-class agent runner.

## Decisions Made

- v1 ships `/weave-execute` as an agent skill workflow only.
- Do not add `weave task execute` in v1.
- Execute means: prepare if needed, ask the user for all/scope/specific task selection when unspecified, implement the selected tasks, verify execution, and update task status locally.
- Execute does not commit, push, open PRs, stash, discard changes, create remote branches, or publish anything remotely.
- `/weave-execute` always runs the existing prepare command for the final selected task set before implementation.
- If prepare reports blockers, execution stops before implementation.
- Dependency truth comes from each task's `Blocked by:` field in `tasks.md`.
- If a selected task is blocked by other tasks, the agent should execute the blocking tasks first according to the dependency order.
- Eligible statuses are `todo`, `in_progress`, and `not_tested`.
- `blocked` tasks can execute only after their `Blocked by:` dependencies are resolved in the same run.
- `done` and `invalid` tasks are skipped by default.
- Multi-task execution continues through later independent tasks when one task fails, but skips downstream tasks blocked by the failed task.
- HITL tasks can be included when explicitly selected or required as dependencies, but the agent must pause for the required human input before continuing.
- Dirty repos already on the expected branch are not a blocker if prepare succeeds.
- Mark a task `in_progress` when execution starts for that task.
- Mark `done` only when implementation is complete and verification passes.
- Mark `not_tested` when implementation appears complete but verification could not run.
- Leave or set `in_progress` with notes when verification fails or implementation remains incomplete.
- Update both the active task index status and the task detail `Status:`.
- Check off only acceptance criteria that were actually satisfied.
- Append concise verification notes under the task being executed.
- Do not rewrite unrelated task wording or unrelated sections.

## Options Considered

- Include commit, push, or PR creation in v1. Rejected as too much side-effect risk for the first execution workflow.
- Add `weave task execute` immediately. Rejected for v1 because implementation is agent behavior, not deterministic CLI behavior.
- Treat selected tasks as an exact set with no dependency expansion. Rejected because `tasks.md` already records `Blocked by:` dependencies and the agent can resolve them.
- Stop the entire run on the first failed task. Rejected in favor of continuing independent tasks and summarizing failures at the end.
- Require clean repos before execution. Rejected; prepare already allows dirty repos on the expected branch and the user wants execution to proceed if prepare succeeds.

## Rejected Approaches

- Execution as prepare-only handoff.
- Execution as status-only bookkeeping.
- Execution as a full publish flow with commits, pushes, and PRs.
- Execution that ignores task dependency metadata.
- Execution that marks tasks done without successful verification.

## User Preferences

- Agent-first workflow.
- `/weave-execute` should ask for task selection when invoked without arguments.
- The agent should infer and resolve dependencies using `Blocked by:`.
- The agent should continue independent work after a task failure.
- If prepare succeeds, dirty selected repos should not block execution.
- Task artifact updates should be useful but not noisy.

## Agent Recommendations

- Keep `/weave-execute` as the user-facing v1 surface and defer `weave task execute`.
- Treat prepare as the safe branch-readiness gate and do not duplicate branch switching inside the execute skill.
- Use per-task execution records: start with `in_progress`, finish with `done`, `not_tested`, or `in_progress` based on verification.
- Use task-local verification first, then the smallest relevant broader check when task verification is absent or weak.
- Keep PRD and architecture work separate after exploration: first produce the product contract, then design the agent workflow and artifact update mechanics.

## Unresolved Points

- Exact no-argument prompt wording for `/weave-execute`.
- Exact summary format after a multi-task run.
- Whether `/weave-execute all` should include HITL tasks automatically or only when needed as dependencies; the current leaning is to avoid autonomous HITL execution unless explicit or dependency-driven.
- Whether execution should record a structured run history outside task-level verification notes.
