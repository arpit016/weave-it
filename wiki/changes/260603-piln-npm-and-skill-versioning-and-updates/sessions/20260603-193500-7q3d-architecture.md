# Session Capture: Architecture - 2026-06-03

## Summary

Plan-mode architecture interview for change `260603-piln-npm-and-skill-versioning-and-updates`. The session began with a deep technical recon of the existing CLI structure ([src/cli.ts](src/cli.ts), [src/commands/](src/commands/), [src/lib/agent-skills.ts](src/lib/agent-skills.ts), [src/lib/files.ts](src/lib/files.ts), [tests/](tests/)) and resolved the highest-blast-radius architecture question: how notices get plumbed into command output. Three plumbing models were evaluated with concrete code-diff comparisons (Option C central renderer vs Option A per-command helper vs Option A+ with enforcement test). After laying out trade-offs, the user proposed a smarter scope simplification: surface notices only on a few entry-point commands rather than universally. The discussion converged on **Tier 1 scoping** - five entry commands carry notices, every other command is unchanged. This preserved the AI-agent surfacing path and the human anchor moment while dropping the central-renderer refactor. The architecture plan was then materialized into the live artifact during this capture.

## Decisions Made

1. Notice plumbing = scoped per-command helper on Tier 1 only. Five commands wrap with `withNotices`: `weave workspace`, `weave change current`, `weave change status`, `weave change new`, `weave status`. All other commands untouched. A test asserts Tier 1 commands include `notices` in `--json` and explicitly that non-Tier-1 commands do not.
2. npm transport = direct HTTPS via Node 22's built-in `fetch` to `https://registry.npmjs.org/weave-it/latest` with 3-second `AbortController` timeout. Zero new dependencies.
3. Cache location = `~/.weave/cache/npm-version.json` (user-level under the existing `.weave/` namespace).
4. Cache TTL = 24 hours.
5. First-run behavior = fire-and-forget background fetch. Process exit is not awaited; first call returns cached value or `null`, populates cache for next call.
6. Opt-out env vars = two layered. `NO_UPDATE_NOTIFIER` (industry-standard) disables the npm check only. `WEAVE_NO_NOTICES` (Weave-specific) disables all notice output.
7. Manifest schema = additive. `installed_from: string | null` added to each `ManifestEntry` in `.weave/agents.yml`. Legacy entries default to `null` ("unknown").
8. Frontmatter parsing = strict for bundled templates. `parseSkillFrontmatter` requires `last_changed_in`. Installed skill files are not re-parsed.
9. Release script = `git describe --tags --abbrev=0` to discover previously published tag. Wired as `npm run release:bump-skills` before `npm publish`.
10. Skill boilerplate = duplicated source, test-enforced byte-identity against a shared constant. No code generation.
11. `lib/notices.ts` is the single source for notice generation. Used by both `withNotices` and `weave status`.

## Options Considered

- Notice plumbing: Option C (universal central renderer, refactor every command), Option A (per-command opt-in helper without enforcement), Option A+ (per-command helper + universal JSON-contract test), and the user-proposed scoping models.
- Tier 1 membership: five-command Tier 1 (chosen), two-command minimal (`weave workspace` + `weave status` only), one-command strict (`weave change new` only), and keep universal Option C.
- npm transport: direct HTTPS, `latest-version` npm package, `update-notifier` npm package, `npm view` shell-out.
- Cache location: `~/.weave/cache/npm-version.json` (chosen), `~/.cache/weave-it/npm-version.json` (XDG), `os.tmpdir()/weave-it-npm-version.json`.
- Cache TTL: 24 hours (chosen), 12 hours, 6 hours, always-live.
- Opt-out env vars: layered (`NO_UPDATE_NOTIFIER` + `WEAVE_NO_NOTICES`, chosen); single `WEAVE_NO_UPDATE_NOTIFIER`; honor only industry-standard `NO_UPDATE_NOTIFIER`.
- Release script tag discovery: `git describe --tags --abbrev=0` (chosen), `npm view weave-it version`, read from CHANGELOG/release-notes.
- Skill boilerplate enforcement: duplicated source + byte-identity test (chosen), generated from a shared snippet at build time, no enforcement.

## Rejected Approaches

- Universal central renderer (Option C): rejected after Tier 1 scoping made it unnecessary - paid for structural invariance across ~15 action handlers when only 5 commands actually need to surface notices.
- "Notices on `weave change new` only" (user's initial proposal): too narrow because skills call `weave workspace --json` and `weave change current --json` during discovery, not `weave change new`. Would break the AI-agent surfacing path entirely and make the skill boilerplate pointless.
- Commander `preAction`/`postAction` hooks only: cannot inject notices into JSON output without each command cooperating; solves nothing.
- `update-notifier` npm package: heavier, opinionated UX that fights the terse footer design.
- `latest-version` npm package: adds a dep for ~50 lines we can write ourselves.
- `npm view` shell-out: slow, requires npm CLI on PATH (not just node).
- Per-repo `~/.weave/` cache: duplicates global state for no gain.
- Aggressive cache TTL (1h, 12h): wastes network for marginal freshness gain.
- Generated skill boilerplate at build time: adds a build step; test-enforced byte-identity is simpler.
- Honor only industry-standard `NO_UPDATE_NOTIFIER`: too narrow; users may want to suppress local skill notices too without also disabling the npm check separately.

## User Preferences

- Strong preference for the smallest refactor that still preserves the AI-agent path and the anchor-moment UX.
- Comfort with introducing a small but precise set of entry-point commands rather than a universal contract.
- Comfort with relying on a CI/release script to manage `last_changed_in` rather than asking contributors to maintain it.
- Comfort with skipping the central-renderer abstraction in favor of explicit per-command wrapping at five well-defined sites.

## Agent Recommendations

- Adopt the Tier 1 scoping for v1; revisit if a future skill needs to discover via a non-Tier-1 command.
- Keep `lib/notices.ts` and `lib/npm-version.ts` strictly pure (injectable `fetch` and clock) so they are easy to unit-test.
- Treat the `--json notices` field on Tier 1 commands as a stable contract: additive changes are fine, removing/renaming fields is a breaking change.
- Document Tier 1 membership in each `templates/skills/<name>/SKILL.md` discovery section so contributors know which commands carry notices when authoring future skills.
- Land `weave-clarify prd` before `weave-issues` so the PRD's universal `notices` contract gets scoped to Tier 1 before tasks are sliced.

## Unresolved Points

Architecture-level open questions (recorded in `architecture.md`):

- Whether the release script should auto-commit `last_changed_in` bumps or write-only and let the maintainer commit (recommend: write-only).
- Whether `weave status` gains `--force-refresh` to bypass the 24h cache (recommend: no for v1; users can `rm ~/.weave/cache/npm-version.json`).
- Whether the notices builder is exposed as a stable internal API for future commands (e.g., a VS Code extension). Not a v1 blocker.

Product-question-raised-by-technical-design:

- The PRD's universal "every command's `--json` output should include a stable top-level `notices` array" is over-scoped now that we've adopted Tier 1. Needs a `weave-clarify prd` pass to enumerate Tier 1 commands and explicitly say other commands do not gain the field.
