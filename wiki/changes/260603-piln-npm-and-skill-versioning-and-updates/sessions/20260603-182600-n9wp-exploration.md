# Session Capture: Exploration - 2026-06-03

## Summary

Interactive product exploration for change `260603-piln-npm-and-skill-versioning-and-updates`. The user explicitly distinguished two version concepts that need notification ("package version" and "skill versions") and asked how to notify users when either upgrades. Eight pivotal product questions were resolved in sequence (skill-version model, notification surfaces, footer scope, audience/delivery, action model, notice content, migration baseline, new-skill behavior). PRD Readiness flipped from `Not ready` to `Ready`.

## Decisions Made

- Skill version model = package-pinned `last_changed_in: <package-version>` in `SKILL.md` frontmatter; a release script automates the bump by diffing `templates/skills/**` against the previously published tag.
- Three layered notification surfaces: passive stderr footer + enriched `weave agent install/update` + new read-only `weave status`.
- Footer scope = two checks: newer-package-on-npm (cached HTTPS) + stale-skills-in-this-repo (local). Inside a Weave repo, surface local drift first. Outside a Weave repo (no `.weave/`), only the npm check fires.
- Dual audience, structured: stderr footer (auto-suppressed by `--json`/CI/non-TTY/env opt-out); stable top-level `notices` array on every `--json` output; skill `SKILL.md` boilerplate surfaces notices via the agent.
- Inform-only action model: CLI never invokes `npm i -g`; notices state facts and point to `weave status`; `weave status` is the single locus for remediation commands.
- Terse notice content: `<skill>: bundled <X>, you installed <Y>[, locally modified]` plus "Run `weave status` for details and remediation commands." No diffs and no remediation commands inline.
- Migration baseline: all existing skills pinned to the package version that introduces `last_changed_in` on day 1. No git-history backfill.
- New skills: `skills_new` notice kind + "New skills available" section in `weave status`. Users install via existing `weave agent install <agent>`. No auto-install.

## Options Considered

- Skill version model: package-pinned (chosen), independent per-skill semver, hash-only with no numeric version, hash-only plus install-time package-version stamp.
- Notification trigger: passive footer + explicit commands (chosen), explicit-only, only on `weave agent install/update`, publish CHANGELOG only.
- Footer scope: both checks (chosen), npm-only, local-only.
- Audience and delivery: dual structured (chosen), human-only stderr, agent-first JSON-only.
- Action model: inform-only with read-only `weave status` (chosen), inform + one-shot `weave update` that also upgrades the global package, inform + interactive `@clack/prompts` walkthrough.
- Modified+stale notice: combined warning notice (initially proposed), two separate notices, modified suppresses stale. User refined to terse facts-only notice that always points to `weave status`.
- Migration baseline: pin all existing skills to the introducing release (chosen) vs backfill via git history.
- New-skill behavior: `weave status` + `skills_new` notice (chosen), no special handling, auto-install on next `weave agent update`.

## Rejected Approaches

- Independent semver per skill - skills do not have an independent distribution channel; release discipline cost is real and the value is theoretical.
- Hash-only with no numeric version - cannot anchor "when did the skill last change," only "changed or not".
- CLI invoking `npm i -g` on the user's behalf - sudo and package-manager-detection (npm/yarn/pnpm/volta/nvm) and global-install fragility outweigh the convenience.
- Interactive `weave outdated` walkthrough - adds code with no decisive UX win over the inform-only model.
- Combined warning notice that lists diff and remediation commands inline - refined down to a terse facts-only notice pointing to `weave status`.
- "Modified suppresses stale" - risks the user permanently losing sight of upstream evolution after one local edit.
- Backfilling `last_changed_in` from git history - high effort, no real user benefit because `installed_from_skill_version` is always >= feature-introduction version anyway.
- Auto-installing brand-new skills on `weave agent update` - mutates repos without explicit user action, a behavior Weave has avoided.

## User Preferences

- Strong preference for inform-only over automation when the action has any chance of going wrong (e.g., `npm i -g`).
- Strong preference for terse notices with a single deeper view (`weave status`) over notices that try to be self-contained.
- Comfortable adding new frontmatter to bundled `SKILL.md` files and accepting a release-time script to maintain them.
- Comfortable with stderr-only footers and `--json` contract additions; agent-context staleness should be first-class, not an afterthought.

## Agent Recommendations

- Adopt package-pinned skill versions for v1; graduate to independent semver only if/when skills become independently distributable.
- Keep the new contract surface small: one new top-level command (`weave status`), one new frontmatter field (`last_changed_in`), one stable additive JSON field (`notices`).
- Defer cache TTL, opt-out env-var naming, npm transport choice, and pre-release dist-tag handling to architecture.
- Defer notice wording, `weave status` output layout, and skill boilerplate text to PRD.
- Reuse existing `weave agent diff` and `weave agent reset` for modified+stale remediation rather than adding new commands.
