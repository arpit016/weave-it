# Session Capture: Architecture - 2026-06-03 (Plan Mode Protocol discovery)

## Summary

Immediately after the architecture lane was captured, the just-completed `/weave-capture` flow exposed a real architectural gap that affects every design-discussion skill across all four supported agents (claude, cursor, codex, opencode). The capture skill landed on the wrong default lane (`prd` instead of `architecture`) because the stored artifact context was last set by `/weave-prd` and never updated by the subsequent `/weave-architect` session - the architect skill instructs the agent to run `weave artifact current set architecture --json` in Plan Mode, but the agent harness blocks the mutation. The skill's justification ("this is local Weave session state, not a repo-tracked artifact, so it's allowed") is correct from Weave's perspective but unenforceable from the harness's perspective. All four agents categorically block filesystem-write tool calls in plan/ask/read-only modes regardless of Weave's distinction. This session converged on a two-phase Plan Mode Protocol, enforced via the same byte-identity-shared-text pattern already locked as Architecture Decision #10 for the notice-surfacing boilerplate.

## Decisions Made

1. **Two-phase Plan Mode Protocol for design-discussion skills.** In Plan/ask/read-only modes: do NOT attempt `weave artifact current set <lane>`. Declare the target lane in the plan output (top and bottom). On plan acceptance (Agent Mode resumes): the FIRST tool call MUST be `weave artifact current set <lane> --json`, before any other work.
2. **Affected skills are `weave-explore`, `weave-prd`, `weave-architect`.** These are the design-discussion skills that today instruct an in-Plan-Mode mutation. `weave-clarify` is borderline (it can run in plan mode too) and should adopt the same protocol if it sets context.
3. **Single source of truth: `templates/skills/<name>/SKILL.md`.** Edit only the templates; `weave agent update --all` propagates to `.claude/`, `.cursor/`, `.opencode/`, `.codex/` (whichever each agent installs into) in one shot.
4. **Enforce protocol drift via byte-identity test.** Introduce a shared constant `EXPECTED_PLAN_MODE_PROTOCOL` exported from a small helper (alongside `EXPECTED_NOTICE_BOILERPLATE` from Architecture Decision #10). Extend `tests/agent-skills.test.ts` to assert every design-discussion skill template contains the exact protocol block. Same enforcement pattern as the notice-surfacing boilerplate - zero new architectural surface.
5. **`weave-capture` becomes defensively smart.** When stored artifact context disagrees with the conversation substance (e.g., stored = `prd`, but the just-completed skill was `weave-architect`), capture should detect the mismatch and ask the user which lane to use. Codify in `templates/skills/weave-capture/SKILL.md` so every agent does the same thing.
6. **Roll this into the active change, not a separate change.** The fix is structurally adjacent to the skill-versioning work (same byte-identity pattern, same release-script story, same `weave agent update --all` propagation, same `last_changed_in` rollout mechanism), so it shares scope cleanly.

## Options Considered

- **Make the CLI mutation a non-filesystem operation that plan mode allows.** Would require Cursor/Claude/Codex/OpenCode to special-case Weave's CLI. Not feasible across four independent agent harnesses.
- **Have the agent in plan mode use a non-tool-call mechanism to signal the lane.** E.g., embed a stable marker like `<weave-artifact-target>architecture</weave-artifact-target>` in the plan output for capture to parse. Brittle, requires capture to read the transcript, and breaks the "CLI is the source of truth for session state" contract.
- **Strengthen the SKILL.md instruction so that the agent in Plan Mode treats the mutation as MUST-RUN.** Conflicts with the host harness's Plan Mode contract. The agent should obey the host. Unenforceable.
- **Have the agent run the mutation as the first action on plan exit.** Chosen. This is the only path that works across all four agents because it relies on instructions the LLM follows, not on harness behavior.
- **Single Plan Mode Protocol section duplicated across skills, no enforcement.** Drift across skills/agents would silently accumulate.
- **Single Plan Mode Protocol section duplicated + byte-identity test.** Chosen, matching the existing Architecture Decision #10 pattern.
- **Generate the Plan Mode Protocol block at build time from a shared snippet.** Adds a build step; byte-identity test is simpler and more transparent.
- **Fix only in `weave-capture` by making it defensive.** Reduces the failure rate but doesn't fix the root cause - the stored context is still wrong, just one consumer is smarter about it.
- **Spin off a dedicated change for the Plan Mode Protocol fix.** Cleaner narrative but adds a second PR for a structurally adjacent fix. Rejected: scope into the current change.

## Rejected Approaches

- "Allowed because it's local session state, not repo-tracked" justification: documented as broken because the host harness doesn't differentiate. The current SKILL.md text in `weave-explore`, `weave-prd`, and `weave-architect` is misleading and should be rewritten.
- Per-skill ad-hoc Plan Mode Protocol text (without a shared constant): rejected for the same reason the notice-surfacing boilerplate is shared - silent drift across the four agents is the failure mode the whole skill-versioning system is supposed to prevent.

## User Preferences

- Strong preference for the fix to work uniformly across all four agents (claude, cursor, codex, opencode) - no per-agent special casing.
- Strong preference to scope into the active change rather than spin a new one, since the fix shares the same byte-identity pattern, release-script behavior, and `weave agent update` propagation as the notice-surfacing work.
- Comfort with treating this as a co-requirement of the notice-surfacing work rather than a separate concern.

## Agent Recommendations

Without this fix, notices on Tier 1 commands may emit confusing or stale lane-based content (and `weave-capture` may land in the wrong artifact, as it nearly did today).
- Add the new Architecture Decision (Two-phase Plan Mode Protocol + shared byte-identity helper) to `architecture.md` as Decision #12, with a corresponding Risk entry and a new Rejected Alternative ("in-Plan-Mode mutation allowed because it's local state").
- Add a new Product Question Raised by Technical Design to `architecture.md`: the PRD currently has no requirement that design-discussion skills set artifact context reliably regardless of agent mode. The PRD needs a co-requirement clause via `/weave-clarify prd`.

The Plan Mode Protocol fix is likely 1-2 task slices: one for the 4 SKILL.md template edits + `weave agent update --all`, one for the byte-identity test + shared helper.

## Unresolved Points

- **Should `weave-clarify` also adopt the Plan Mode Protocol?** It can run in plan mode and currently does not set artifact context (it operates on the artifact the user explicitly names). Recommend: yes, even though it doesn't set context, the protocol section is harmless and ensures uniform behavior.
- **Should `weave-next` (read-only, no mutations) gain the protocol section?** It does not set context and does no mutations, so the protocol is vacuous. Recommend: no, to keep the byte-identity surface narrow.
- **Where exactly in each SKILL.md should the protocol block live?** Recommend: immediately after the existing `# Plan Mode Guard` section (which already exists in `weave-explore`, `weave-prd`, `weave-architect`) and before the discovery commands. Replaces the misleading "Setting artifact context writes local Weave session state only ... is allowed" sentence.
- **Should the protocol block include a literal text template for the "next action on plan exit" directive?** Recommend: yes, so the LLM has a single canonical phrasing to emit. E.g., `On plan acceptance, the first action will be: weave artifact current set <lane> --json`.
- **Should `weave-capture`'s defensive check be opt-in or always-on?** Recommend: always-on, with a documented override (user passes an explicit lane to bypass the check).
