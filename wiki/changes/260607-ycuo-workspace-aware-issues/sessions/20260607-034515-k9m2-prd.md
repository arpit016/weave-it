# Session Capture: PRD - 2026-06-07

## Summary

Explored how `weave-issues` should work for workspace and multi-repo changes where backend and frontend engineers plan separately but still need coherent tracer-bullet implementation tasks. The discussion converged on keeping one canonical `tasks.md` per change while adding scope-aware task generation and repo-location metadata.

## Decisions Made

- Keep `wiki/changes/<change-id>/tasks.md` as the single canonical tasks artifact.
- Do not create `tasks/<repo>/tasks.md` or per-repo task artifacts.
- Add `Scope` as a free-form planning and ownership label for generated tasks.
- Common scope labels are `backend`, `frontend`, and `full-stack`, but the skill must not enforce a rigid taxonomy.
- `Scope` is not a repo name, architecture facet name, or technical layer.
- `weave-issues backend` means backend-owned tracer-bullet slices using all relevant source context.
- `weave-issues frontend` means frontend-owned tracer-bullet slices using all relevant source context.
- A scoped run may generate `Scope: full-stack` tasks when the smallest meaningful behavior crosses backend and frontend boundaries.
- Each task should include implementation-location metadata so future agents know where the tracer bullet belongs.
- Multi-repo tasks should include `Repo Involvement` as guidance only; it must not become subtask tracking or per-repo status.

## Options Considered

- Per-repo task files under `tasks/<repo>/tasks.md`.
- Single `tasks.md` with repo-specific sections.
- Single `tasks.md` with task-level scope and repo-location metadata.
- Fixed scope taxonomy including `mobile`, `contracts`, `infra`, and `docs`.
- Repo-specific executable rows with per-row status.

## Rejected Approaches

- Per-repo task files were rejected because they make repo boundaries look like task boundaries, complicate cross-repo tracer bullets, and create a sub-lifecycle inside one change.
- A rigid scope legend was rejected because it introduces unnecessary taxonomy; teams usually speak in terms of backend and frontend, and mobile often fits the frontend mental model.
- Execution tracking inside tasks was rejected for now; the current change should focus on task generation and planning semantics only.

## User Preferences

- Prefer simple, common language over rigid workflow taxonomy.
- Prefer `backend`, `frontend`, and `full-stack` as normal examples.
- Treat DB work as backend by default.
- Do not introduce first-class `contracts`, `mobile`, `infra`, or `docs` scopes unless users naturally provide those labels.
- Do not handle task execution behavior in this change.

## Agent Recommendations

- Keep one canonical task file and make task generation scope-aware.
- Strengthen `weave-issues` language so scoped tasks remain tracer bullets, not backend/frontend layer lists.
- Add `Scope`, `Primary repo`, `Repos`, `Architecture refs`, and `Coordination` fields to each task.
- Add `Repo Involvement` for multi-repo tasks so implementation agents have enough breadcrumbs to find code and verification anchors.
- Update `weave-issues` rerun behavior so scoped reruns reconcile relevant tasks while preserving unrelated scopes.

## Unresolved Points

- Exact formatting of `Repo Involvement` columns may be adjusted during implementation.
- Whether the opencode command wrapper should document scoped invocation examples is implementation-dependent.
