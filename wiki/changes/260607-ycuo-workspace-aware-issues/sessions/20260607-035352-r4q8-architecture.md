# Session Capture: Architecture - 2026-06-07

## Summary

Captured the architecture dissection for making `weave-issues` scope-aware while preserving one canonical `tasks.md`. The discussion concluded that this is primarily a skill-template and documentation change, not a CLI/runtime change.

## Decisions Made

- Keep `wiki/changes/<change-id>/tasks.md` as the only `issues` artifact.
- Implement scope-aware behavior inside the `weave-issues` skill instructions, not as a new CLI parser feature.
- Treat `Scope` as task metadata for planning and ownership, not as a repo selector, architecture facet selector, technical layer, lifecycle lane, or artifact target.
- Preserve the existing `issues` lifecycle lane and `weave change progress issues` behavior.
- Add task metadata for `Scope`, `Primary repo`, `Repos`, `Architecture refs`, and `Coordination`.
- Add `Repo Involvement` only as implementation-location guidance for multi-repo or ambiguous-location tasks.
- Do not add per-repo task files, per-repo statuses, execution semantics, or a rigid scope taxonomy.
- Update the canonical skill template and installed copies so they remain byte-identical where expected.

## Options Considered

- Adding new CLI/runtime support for scoped `weave-issues` invocations.
- Keeping the change entirely in the `weave-issues` skill template.
- Updating the opencode command wrapper to advertise scoped examples.
- Creating separate architecture facets for API/contracts or frontend-backend integration.

## Rejected Approaches

- New runtime parsing was rejected because slash command arguments already flow into the skill as context, and this change changes agent behavior rather than CLI behavior.
- Per-repo task artifacts were rejected because they conflict with the single workspace change artifact model and fragment tracer bullets.
- Repo-row statuses were rejected because execution tracking is out of scope for this change.
- A rigid set of scope labels was rejected because users should keep common team language such as `backend`, `frontend`, and `full-stack` without being forced into a taxonomy.

## User Preferences

- Keep the model simple and language-driven.
- Use `backend`, `frontend`, and `full-stack` as examples, not enforced categories.
- Avoid adding execution-specific behavior in this change.
- Prefer one canonical task artifact with enough repo-location breadcrumbs for future implementers.

## Agent Recommendations

- Update `templates/skills/weave-issues/SKILL.md` in five areas: scope argument handling, workspace/repo context discovery, scoped tracer-bullet rules, task artifact shape, and scoped rerun reconciliation.
- Update `.agents/skills/weave-issues/SKILL.md` and `.claude/skills/weave-issues/SKILL.md` to match the canonical template.
- Update `tests/agent-skills.test.ts` with assertions for the new scope/repo-location wording.
- Update `wiki/knowledge/domains/change-workflow/features/weave-issues/behavior.md` after implementation.
- Treat the opencode command wrapper as optional; update it only if scoped usage examples should be discoverable from the command description.

## Unresolved Points

- Whether to update the opencode wrapper wording in this change or leave scoped examples only in the skill body.
- Whether `Repo Involvement` should be required only for multi-repo/ambiguous tasks or for every task; the architecture recommendation is multi-repo/ambiguous only.
