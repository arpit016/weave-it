# Session Capture: Architecture - 2026-05-31

## Summary

Designed the technical approach for explicit change lifecycle tracking.

The architecture centers lifecycle mutation in a CLI-owned helper, `weave change progress <lane> --json`, so skills do not independently hand-edit `status.yml`. `stage` remains the highest reached lane, while `stale` records downstream invalidation state in `status.yml`.

The target change is `260531-d6bx-explicit-change-stage-and-stale-downstream`.

## Decisions Made

- Use `status.yml` as the change-level lifecycle source.
- Keep stage order as `exploration -> prd -> architecture -> issues`.
- Add `weave change progress <lane> --json` as the lifecycle mutation command.
- Store stale state as a metadata map keyed by lane.
- Include `invalidated_by` and `invalidated_at` on each stale lane.
- Keep `artifact current` limited to `exploration`, `prd`, and `architecture`; `issues` is a lifecycle lane, not an artifact context.
- Make old changes backward compatible by treating missing stale state as empty.
- Use artifact evidence to infer reached downstream lanes for older changes with stale `stage: exploration`.
- Make `weave-next` recommend the earliest stale lane before forward progress.
- Make `weave-issues` warn and require explicit confirmation when architecture is stale.

## Options Considered

- Stale state as a lane list.
- Stale state as a boolean map.
- Stale state as a metadata map.
- Lifecycle helper named `weave change progress`.
- Lifecycle helper named `weave change stage`.
- Lifecycle helper under `weave artifact`.
- `weave-issues` refusing outright when architecture is stale.
- `weave-issues` only warning without confirmation.

## Rejected Approaches

- Rejected lane list and boolean map stale shapes because they lose invalidation cause and timing.
- Rejected `weave change stage` because the helper manages both stage advancement and stale invalidation.
- Rejected `weave artifact progress` because lifecycle state belongs to the change, not current artifact context.
- Rejected hard refusal in `weave-issues` for v1 because the user prefers warning with explicit continuation.
- Rejected passive warning only because stale architecture should create a clear decision point before issue generation.

## User Preferences

- Prefer lane-aware lifecycle semantics.
- Prefer explicit highest-reached stage plus stale downstream markers rather than regressing stage.
- Prefer stale metadata in `status.yml`, not artifact frontmatter.
- Prefer deterministic CLI ownership of lifecycle mutation.
- Prefer `weave-issues` warning with explicit continuation when architecture is stale.
