# Session Capture: Exploration - 2026-05-31

## Summary

Explored why `status.yml.stage` never changes after exploration and defined the desired lifecycle behavior.

The investigation found that stage is currently created as `exploration`, then only read and displayed. No current command or skill advances it after PRD, architecture, or issues work.

The agreed direction is to make `status.yml` own explicit change lifecycle progress and downstream stale state.

## Decisions Made

- Track this as a new Weave change, separate from lane-aware session-only capture.
- Treat `status.yml.stage` as explicit lifecycle state.
- Use lane-aligned stage values for v1: `exploration`, `prd`, `architecture`, and `issues`.
- Do not add `implementation` in v1.
- Define `stage` as the highest reached lane.
- Add stale/downstream invalidation state in `status.yml`.
- Do not store stale state in artifact frontmatter.
- Weave-managed artifact writes should update stage and stale state.
- Do not infer stale state from arbitrary manual file edits in v1.
- When an earlier lane is revised, keep the highest reached stage and mark downstream lanes stale.
- Refreshing a stale lane clears only that lane.
- Downstream stale lanes remain stale until refreshed by their own lane workflow.
- `weave-next` should recommend the earliest stale lane before forward progress.
- `weave-issues` should warn or refuse when architecture is stale.

## Options Considered

- Explicit lifecycle state: selected because `status.yml.stage` should be authoritative instead of static display metadata.
- Derived progress only: rejected because it leaves `status.yml` stale and makes tools rederive state repeatedly.
- Removing stage: rejected because status output is intended to communicate lifecycle progress.
- Pure stage regression: rejected because it hides how far the change had progressed.
- Stage plus stale metadata: selected because it preserves progress while making rework visible.
- Timestamp/git inference for stale state: rejected for v1 because manual edits, rebases, and copied changes make it brittle.

## Rejected Approaches

- Do not regress `stage` as the only invalidation mechanism.
- Do not treat downstream artifacts as fresh after an upstream artifact changes.
- Do not add an implementation stage until Weave owns an implementation workflow.
- Do not duplicate stale state between `status.yml` and artifact frontmatter.

## User Preferences

- The user wants `stage` to be meaningful and explicit.
- The user wants downstream artifacts to become stale when upstream artifacts change.
- The user prefers preserving reached progress while showing rework.
- The user wants stale state in `status.yml`.
- The user wants stale state updated by Weave-managed artifact writes.

## Agent Recommendations

- Add a deterministic CLI helper for stage/stale updates so skills do not hand-edit YAML independently.
- Keep `status.yml` as the change-level lifecycle source.
- Update `weave-next` to prioritize stale lanes over forward progress.
- Update issue generation to warn or stop when architecture is stale.
- Keep v1 stage values aligned with artifact lanes.

## Unresolved Points

- Exact YAML shape for stale markers.
- Exact CLI helper name.
- Whether stale markers should include timestamps and invalidating lane names in v1.

## Live Artifact Updates Applied

Created and populated `exploration.md` for explicit change stage and stale downstream artifacts.

## Next Resume Point

Generate the PRD. Focus on user-facing lifecycle semantics: highest reached stage, stale downstream lanes, Weave-managed artifact writes as lifecycle triggers, stale-first `weave-next` recommendations, and no v1 implementation stage.
